# Приложение для записи кастомной прошивки в приборку BMW KMBI_PL2 через D-CAN

**Анализ проекта и план разработки.**
Объект: щитки приборов BMW PL2 — `HKOML2`, `DKOML2`, `BKOML2`, `KOMBL2`
(E8x / E9x / E84 / E89), МК **Fujitsu/Spansion MB90F395HA** (F2MC-16LX,
512 КБ flash @ `0xF80000–0xFFFFFF`, 30 КБ RAM).
Диагностический SGBD: **`KOMB87.prg`**. Скрипт прошивки: **`08FLASH 8.01`**
(`080100HKOML2.ipo` / `080101DKOML2.ipo`).

Документ опирается только на артефакты, лежащие в этом проекте, плюс явно
помеченные внешние источники. Всё, что является гипотезой, помечено
«**гипотеза**»; всё остальное — воспроизводимый факт с указанием, чем он
проверяется.

---

## Цель и рамки (подтверждено владельцем)

**Цель:** программное обеспечение, позволяющее заливать **кастомную прошивку
в приборку KMBI_PL2 по проводу, без программатора** — тот же класс продукта,
что `xHP Flashtool` (кастомные прошивки в АКПП ZF 6HP/8HP через D-CAN) и
`MHD Flasher` (моторы N54/N55 через OBD).

**Чего мы НЕ делаем:**

* не подбираем и не ломаем RSA-ключи подписи BMW;
* не пытаемся обойти `AUTHENTISIERUNG` «в лоб» как самоцель;
* не пишем собственный flash-стек с нуля, если этого можно избежать (§ 7.1).

**Что это меняет по существу.** `xHP` и `MHD` работают **не** потому, что
взломали криптографию, а потому что эксплуатируют **непокрытые подписью
области** — это документированный класс атаки (MSD80/81, § 10.2): подпись
покрывает не весь образ, а диапазоны из таблицы, и **сама таблица подписью не
покрыта**. То есть наша задача — не криптоанализ, а **поиск того, что подпись
не покрывает**: непокрытый диапазон, непокрытая таблица диапазонов либо
патченый загрузчик. Это ровно гипотеза **H2** плана и ровно то, что делают
коммерческие флешеры.

**Следствие для ожиданий:** проект находится в том же классе, что `xHP`/`MHD`,
а не в классе «сломать RSA-1024». Это существенно повышает шансы.

**Рамки (уточнены владельцем):**

* **Целевые приборки — вся линейка PL2**: `HKOML2`, `BKOML2`, `DKOML2`, `KOMBL2`.
* **Окружение для первых экспериментов** — Windows-ПК с установленными
  BMW Standard Tools (EDIABAS).
* **Что должна делать кастомная прошивка:**
  1. вывод **всех доступных показателей** и в верхнюю, и в нижнюю часть дисплея;
  2. смена отображения передачи: не просто `D`/`S`, а `D1…D6`, `S1…S6`;
  3. вывод **8 передач** — требование свапа АКПП на ZF 8HP;
  4. **стратегическая цель — «генератор прошивки»**: пользователь выбирает свою
     приборку (программа сама читает её версию), отмечает галочками нужные
     параметры и получает прошивку.

## 0. Краткий вывод

1. **Штатный путь прошивки закрыт.** Любая правка флеша ломает
   `FLASH_SIGNATUR_PRUEFEN`; перед записью обязательна `AUTHENTISIERUNG`
   (challenge-response). Через WinKFP/E-Sys кастомный образ залить нельзя.
2. **Барьер — именно подпись, а не аутентификация.** Секрет `AUTHENTISIERUNG`
   *обязан* лежать в `KOMB87.prg` (аутентификация выполняется офлайн, на каждой
   машине с WinKFP) — то есть восстановим. Приватный ключ
   `NG_SIGNATUR_PRUEFEN` — только у BMW. Но обход аутентификации остаётся
   **необходимыми воротами** для любой записи, поэтому обе задачи нужны.
   **Второй, независимый барьер:** резидентный код с векторами CPU лежит в
   `0xFFC000–0xFFFFFF`, которого **нет ни в одном** из 14 имеющихся файлов
   `.0pa`/`.0ba`. Для части стратегий его дамп не обязателен (H2 работает по
   таблице диапазонов подписи внутри приложения, которое у нас есть), но для
   «эксплойта бутлоадера» в узком смысле — обязателен.
3. **Зато найден нетривиальный и, похоже, недооценённый артефакт:**
   `DKOML2/H01028K_0102FH.0ba` — это **не** кусок прикладной прошивки
   (совпадение с `.0pa` всего 3 %), а маленькая самодостаточная программа
   (25 280 байт) с **собственной таблицей векторов**, где все 40 записей
   указывают на один stub. Это либо **временный ядро-программатор**
   («flash kernel»), либо **образ самого загрузчика (BSU)** — в обоих случаях
   это принимаемый приборкой исполняемый образ, и загрузчик KOMBI
   **перезаписываем** (в отличие от C167 с mask-ROM). См. § 4.3 и § 5, H4.
4. **Четыре пути**, в порядке «шансы / стоимость»:
   **(A)** чтение `0xFFC000+` штатным сервисом памяти `SPEICHER_LESEN` — даёт
   дамп загрузчика по D-CAN;
   **(B)** атака «непокрытый диапазон» в стиле MSD80 — **ключи не нужны**,
   кандидат-«карман» (`0xFB9FF0–0xFBBFFF`, 8 208 Б) уже найден;
   **(C)** патч ядра-программатора `.0ba`;
   **(D)** собственно эксплойт бутлоадера в узком смысле.
   Пути **A и B** надо проверить первыми: A — потому что дёшево, B — потому
   что не требует ни ключей, ни дампа защищённой области.
5. **Критически не хватает одного файла — `komb87.prg`** (BMW SP-Daten E89
   v69.0, `BASE/ecu/`). Он декодируется имеющимся `decoderPrg.py` и содержит
   точные телеграммы всех flash-джобов, включая параметры
   `PABD-TestSchluesselAuthentisierung`. Это самый дешёвый способ получить
   половину ответов.

## 2. Как прошивка устроена сегодня (полная цепочка)

```
WinKFP  ──►  EDIABAS  ──►  K+DCAN кабель  ──►  D-CAN 500 кбит/с  ──►  KOMBI
   │            │
   │            └─ скрипт 08FLASH 8.01 (.ipo), 18 джобов
   └─ Zusbauvorschrift: HW-NR → ровно один .0pa
```

Порядок джобов в `.ipo` (из строк самого файла, полный список 18):

| # | Джоб | Назначение |
|---|---|---|
| 1 | `UProgLesen` | чтение U-Prog |
| 2 | `GetDiagProt` / `SetDiagProt` | выбор диагностического протокола (переключение в D-CAN) |
| 3 | `SetEcuAdr` | адрес ЭБУ |
| 4 | `VersionInfo` / `Ident` / `FehlerLoeschen` | идентификация |
| 5 | `AifLesen` / `HwReferenzLesen` / `DatenReferenzLesen` | AIF, HW- и Daten-Referenz |
| 6 | `ZifLesen` / `ZifBackupLesen` | Zulieferer-Info-Feld и его бэкап |
| 7 | **`PhysHwNrLesen`** | физический HW-NR → выбор образа |
| 8 | **`Authentisierung`** | `SERIENNUMMER_LESEN` → `AUTHENTISIERUNG_ZUFALLSZAHL_LESEN` → `AUTHENTISIERUNG_START` |
| 9 | **`LoescheFlash`** | `NG_FLASH_LOESCHEN`, ожидание `RoutineNotComplete` → OKAY |
| 10 | **`FlashSchreiben`** | `FLASH_SCHREIBEN_XXL`, `FLASH_SCHREIBEN_ADRESSE`, `FLASH_BLOCKLAENGE_DATEN`, `BufferAuffuellen` |
| 11 | `FlashSchreibenEnde` | завершение записи |
| 12 | **`PruefeSignatur`** | `NG_SIGNATUR_PRUEFEN`, ожидание `RoutineNotComplete` → OKAY |
| 13 | `SGReset` | `STEUERGERAETE_RESET` |

Ключевые строки из `.ipo`, подтверждающие схему аутентификации:

```
SERIENNUMMER_LESEN, SERIENNUMMER
AUTHENTISIERUNG_ZUFALLSZAHL_LESEN (3;
AUTHENTISIERUNG   Authentisierungsart :
    Asymetrisch  T_SMA
    Symetrisch   T_SMB
    Simple       T_SMC
  Key :  Schluessellaenge
NG_AUTHENTISIERUNG_START
```

То есть: ЭБУ отдаёт случайное число; тестер отвечает подписью; **режим
(`SMA`/`SMB`/`SMC`) и длина ключа — параметры**, а не константы.

## 3. Три барьера

### 3.1. `AUTHENTISIERUNG` (challenge-response)
`SERIENNUMMER_LESEN` → `AUTHENTISIERUNG_ZUFALLSZAHL_LESEN("3;0x<userID>")` →
`AUTHENTISIERUNG_START(<блоб>)`. Судя по документированному аналогу BMW MS45
(§ 10.1), блоб = заголовок EDIABAS + **RSA-512 подпись** 64 байта + `0x03`,
где подпись считается как `MD5(userID ‖ serialNumber ‖ seed)^d mod n`.

### 3.2. `FLASH_SIGNATUR_PRUEFEN`
Вызывается **после** записи как `$31` routine **`$09` CheckSignature** с
аргументом `BEREICH` ∈ {`'Programm'`, `'Daten'`}. Из таблицы `PROGRAMMIERSTATUS`
в SGBD видно, что проверок **две и они раздельные**:

| Код | Текст |
|---|---|
| `0x05` | `Signaturprüfung PAF nicht durchgeführt` |
| `0x06` | `Signaturprüfung DAF nicht durchgeführt` |

**PAF** = Programm-Austausch-Datei, **DAF** = Daten-Austausch-Datei. Это
структурно совпадает с MS45, где подпись вызывается как `Daten;64` /
`Programm;64` — и это **основа для H2** (§ 5): если проверяемых диапазонов
несколько и они задаются таблицей, критично, покрыта ли таблица подписью.
Для KOMBI подписи нет в открытом виде — ключ только у BMW.

### 3.3. Аутентификация ≠ подпись — и это меняет всю стратегию

| | `AUTHENTISIERUNG` | `NG_SIGNATUR_PRUEFEN` |
|---|---|---|
| Кого проверяют | ЭБУ проверяет **тестера** | ЭБУ проверяет **свою прошивку** |
| Где секрет | **У тестера** → обязан лежать в `KOMB87.prg` (аутентификация идёт офлайн, на каждой машине с ISTA/WinKFP) | Приватный ключ **BMW** — не лежит нигде |
| Восстановим? | **Да, принципиально**: раз WinKFP проходит аутентификацию без интернета, ключевой материал есть в SGBD | Только BMW — или обход |
| Что даёт обход | право **записать** | право **запустить** |

**Следствие, которое надо держать в голове:** обход `AUTHENTISIERUNG` сам по
себе бесполезен — `PruefeSignatur` вызывается в том же скрипте и опрашивается
в цикле до `RoutineNotComplete`, то есть пропустить его нельзя. Но обход
аутентификации — **необходимые ворота** для стратегии B (§ 5, H4): залить
патченый `.0ba`.

**Отдельное предупреждение.** Байт синхронизации `0x00` и ответ `0xC5` —
это **Infineon C167** (MS42/MS43/ME7.x, BSL в mask-ROM), а **не** F2MC-16LX.
Для MB90F395HA подобного «байта входа» и команд вида `0x0D` публично не
найдено. Переносить протокол C167 на нашу приборку нельзя.

### 3.4. Защищённая область и ABI
См. § 4.1–4.3. Даже имея подпись, нельзя переписать загрузчик — а именно
там живут векторы и, вероятно, монитор программирования.

## 4. Новые факты, полученные в этом анализе

### 4.1. Область `0xFFC000–0xFFFFFF` не пишется ни одним файлом — доказано

Проверено по **всем 14** файлам (`4 × DKOML2 .0pa`, `9 × HKOML2 .0pa`,
`1 × .0ba`), `tools/parse_ihex.py`:

| Свойство | Значение для всех 14 файлов |
|---|---|
| максимальный покрытый адрес | `0xFFBFEF` |
| байт в `0xFFC000–0xFFFFFF` | **0** |
| «дырка» в конце каждого 64-КБ банка (`0x…FFF0–0x…FFFF`) | **8 банков из 8** |
| низкий блок `0x000000–0x00EFEF` | есть только у DKOML2 (61 424 Б) |

Это не совпадение, а структурное свойство формата. Регион `0xFFC000–0xFFFFFF`
(16 КБ) — резидентная, не обновляемая по OBD область. По документации
F2MC-16LX таблица векторов прерываний расположена в старших адресах
(в [доп. тех. информации F2MC-16LX](https://www.infineon.com/assets/row/public/documents/30/57/infineon-cy90880-series-f2mc-16lx-hardware-manual-additionaltechnicalinformation-en.pdf)
перечислены адреса векторов вида `FFFFBA`), то есть **векторы CPU попадают
именно в непокрытую область**.

**Следствие для проекта:** бутлоадер/монитор в наших руках отсутствует.
Его нужно добыть (см. § 5, H1/H3) — без этого эксплойт проектировать не из чего.

### 4.2. Таблица ABI приложение ↔ загрузчик: 40 записей × 4 байта @ `0xFFBF50`

`0xFFBF50–0xFFBFEF` = ровно 160 байт = **40 указателей по 4 байта (LE, 24-бит)**.
Разбор:

| Файл | «заглушка» (default) | Реальные обработчики |
|---|---|---|
| `HKOML2/9316169A.0pa` | `0x00FB9FC8` | `0x00FDA504`, `0xFDA516`, `0xFDA528`, `0xFDA53A`, `0xFDA54C`, `0xFDA55E`, `0xFDA570`, `0xFDA582`, `0xFDA594` |
| `HKOML2/9168320A.0pa` | `0x00FAFFA8` | `0x00FD73E3` … `0x00FD7473` (9 шт., шаг `0x12`) |
| `DKOML2/9347674A.0pa` | `0x00F9FFF8` | `0x00FF0099`, `0xFF0075`, `0xFF0087`, `0xFF002D`, `0xFF003F`, `0xFF00CF`, `0xFF00AB`, `0xFF00BD`, `0xFF0009`, `0xFF001B` |
| **`DKOML2/H01028K_0102FH.0ba`** | — | **все 40 записей = `0x00F869D7`** |

Запись 0 во всех `.0pa` = `0xFFFFFFFF`.

**Интерпретация (гипотеза, высокая уверенность).** Это публикуемая
приложением таблица обработчиков, которую читает резидентная область: CPU-векторы
в `0xFFC000+` передают управление через неё. Записей ровно 40, реальных
обработчиков 9–10 (остальные — заглушка). Стабильность расположения
(`0xFFBF50`, последние 160 байт прикладной области) и то, что это
**единственный не-кодовый сегмент в `.0ba`**, делают версию убедительной.

**Следствие:** это контракт, который обязана выполнять любая кастомная
прошивка. И это же — самая удобная точка точечного патча (§ 5, H4).

**Уточнение после разбора SGBD.** ID рутин, которые приборка обязана
обслуживать, теперь известны точно (`$31` → `$02` ClearMemory, `$07`
RequestForAuthentication, `$08` ReleaseAuthentication, `$09` CheckSignature,
`$0A` статус; плюс `$23`, `$34`, `$36`, `$3D`). Это делает таблицу
`0xFFBF50` опознаваемой: искать в прошивке диспетчер по этим ID и
сопоставлять его обработчики с 9–10 «настоящими» записями таблицы.
Похоже, что это и есть таблица диспетчеризации `NG_*`-рутин, а не просто
векторы прерываний.

### 4.3. `.0ba` — не фрагмент приложения, а отдельная программа

Сравнение `H01028K_0102FH.0ba` с каждым из 4 `.0pa` DKOML2 по его собственным
диапазонам (`0xF80000–0xF83820`, `0xF84050–0xF86A50`, `0xFFBF50–0xFFBFF0`):
**совпадение 3 %** (882–913 из 25 280 байт). То есть `.0ba` — не «кусок»
приложения и не его инкрементальная дельта.

Что он пишет:

| Сегмент | Длина |
|---|---|
| `0xF80000–0xF8381F` | 14 368 |
| `0xF84050–0xF86A4F` | 10 752 |
| `0xFFBF50–0xFFBFEF` | 160 (таблица векторов, **пишется последней**) |

Заголовок файла:
```
;Austausch-Datei    Programm
$REFERENZ 01028K0F130S H
$BSU_REFERENZ_NEW 0102FH O
$BSUTIME 0x0005 G
$CHECKSUMME B964 J
```

Целевой stub `0xF869D7` дизассемблируется в **осмысленный F2MC-код** —
канонический «ловушечный» обработчик прерывания:

```
F869D7: 0800   LINK 0x00
F869D9: 60fe   BRA  0xF869D9      ; вечный цикл
F869DB: 09     UNLINK
F869DC: 6b     RETI
```

**Две конкурирующие интерпретации — их надо различить, это влияет на план:**

- **(I) Временное ядро-программатор** (моя версия). `.0ba` кладётся в область
  данных приложения, переводит все прерывания на себя и выполняет
  стирание/запись. Косвенный аргумент: `0xF80000–0xF9BFFF` — это
  таблицы/данные (`HANDOFF.md`, факт №5), код приложения начинается только с
  `0xF9C000`, поэтому запись туда не разрушает работающую программу.
- **(II) Образ самого загрузчика (BSU)** (версия внешнего исследования).
  Тогда `0xF80000–0xF86A4F` — резидентный загрузчик, а `$BSU_REFERENZ_NEW 0102FH`
  — его собственная версия. Косвенный аргумент: поле `$BSU_*` и то, что
  перезапись загрузчика штатно предусмотрена, — чего у C167 с mask-ROM BSL нет.

Общее у обеих версий и главное для нас: **`.0ba` — официальный, принимаемый
приборкой исполняемый образ, и загрузчик KOMBI перезаписываем.** Это лучший
кандидат на эксплойт из всего, что есть (§ 5, H4).

**Решающий тест.** Прямой прогон `f2mc_cfg.py` по `.0ba` оказался
неинформативным (714 «функций» на 25 КБ — очевидная переразметка из-за
старта внутри Ident-заголовка; корректный диапазон кода ещё надо определить).
Различить версии можно так: найти в `.0ba` код, работающий с UART/`SIN`/`SOT`
(версия II — это последовательный загрузчик) либо с CAN/KWP2000-диспетчером
(версия I), и сопоставить 40 указателей `0xFFBF50` с `NG_*`-рутинами.

Что осталось невыясненным в любом случае: кто и как проверяет подпись
**самого** `.0ba`, и как ядро сосуществует с приложением в момент, когда оно
само попадает под перезапись. Ответит разбор `komb87.prg` и дамп
защищённой области.

### 4.4. Низкий блок `0x000000–0x00EFEF` (только DKOML2) — это не код

- 61 424 байт, присутствует **только** в 4 файлах DKOML2, нет ни в одном HKOML2.
- Первые 64 байта выглядят как таблица 16-битных значений
  (`0x0A0F`, `0xFEFE`, многократно `0x580B`, далее `0x577A`, `0x5784`, …).
- Значения `0x577A…0x57E3` указывают на **11 записей по 10 байт** с
  сигнатурой `B1 B7 81 4C 9A … 9B EC 55` — это фиксированный формат данных,
  а не код (подтверждает и уточняет факт №6 из `HANDOFF.md`).
- Линейный свип «декодируется» без ошибок, но даёт бессмыслицу — типичный
  признак данных.
- Энтропия по блокам 8 КБ: `0x0000–0x6000` ≈ 6.6–6.8 (плотные данные),
  `0x6000–0xA000` 3.4–4.3, `0xA000` и выше — 0.15 и ниже (почти константа,
  периодический шаблон/заполнитель).

**Статус: назначение не установлено.** Важно, что этот диапазон **не входит**
в окно внутреннего флеша `0xF80000–0xFFFFFF`, то есть это либо другое
устройство памяти, либо другое адресное пространство. Практический вопрос:
**должно ли приложение-прошивальщик обрабатывать этот блок отдельно для
DKOML2** — открыт.

### 4.5. `.ipo` — отдельный, пока не декодируемый контейнер

`decoderPrg.py` на `.ipo` падает (`ValueError` при разборе info-секции) —
формат другой. Карта энтропии файла `080100HKOML2.ipo` (46 880 Б):

| Диапазон | Энтропия | Печатных | Что это |
|---|---|---|---|
| `0x0000–0x7FFF` | ~4.0 | 8–12 % | **байт-код** |
| `0x8000–0xB71F` | ~5.4 | 65–74 % | таблица строк/символов |

Внутри найдены (проверено `grep` по бинарю):

```
;ProzessorTyp =            (варианты: "Standard", "HC12DG128")
PABD-Modulname / -Revision / -Author / -SGFamilie / -SG_MAXANZAHL_AIF
PABD-ProgrammUndDaten
PABD-ProzessorTyp
PABD-AuffuellenSwitch
PABD-DynamischeMXBL
PABD-WiederaufsetzenBlockSwitch
PABD-WartenNachECUProgrammMode
PABD-TestSchluesselAuthentisierung   ← тестовый ключ аутентификации
PABD-WiederaufsetzenSwitch
PABD-SgInnenTemperaturLesen
PABD-SgPhysHwNrLesen
```

Два практических вывода:

1. **`PABD-TestSchluesselAuthentisierung`** — в скрипте прошивки есть штатное
   понятие «тестовый ключ аутентификации». Если для KOMBI он активен, это
   готовый обход `AUTHENTISIERUNG`. Проверяется декодированием значений PABD.
2. **`ProzessorTyp` = `Standard` | `HC12DG128`.** Наличие `HC12DG128`
   (Motorola/Freescale HCS12) в скрипте для приборки на **F2MC-16LX** требует
   объяснения. Наиболее вероятно — это таблица поддерживаемых типов в
   *универсальном* `08FLASH 8.01`, и выбрано `Standard`. Но это же может быть
   указанием на **второй процессор** в щитке. Проверяется декодированием
   значения `ProzessorTyp` — ср. с необъяснённым низким блоком DKOML2 (§ 4.4).

### 4.6. `$CHECKSUMME`: алгоритм не воспроизведён (блокер для H4)

Каждый файл содержит строку-директиву вида `$CHECKSUMME <hex> <символ>`:

| Файл | `$CHECKSUMME` | Длина данных |
|---|---|---|
| `HKOML2/9316169A.0pa` | `F69F C` | 499 568 |
| `HKOML2/9168320A.0pa` | `472B R` | 499 568 |
| `DKOML2/9213308A.0pa` | `B0F8 5` | 531 328 |
| `DKOML2/9347674A.0pa` | `99E4 1` | 546 112 |
| `DKOML2/H01028K_0102FH.0ba` | `B964 J` | 25 280 |

Замыкающий одиночный символ — это, по-видимому, **check-символ строки**
(такие же есть у всех `$`-директив: `$REFERENZ … H`, `$BSU_REFERENZ_NEW … O`,
`$BSUTIME 0x0005 G`, `$VALUE_UNUSED_BYTE 0xFF J`), а не тип checksum.

**Проверено 18 гипотез на всех 14 файлах, совпадений — 0:**
сумма 8-бит (обычная и с end-around carry), XOR 8-бит, суммы 16- и 32-битных
слов LE/BE, суммы с примешиванием адреса, 8 вариантов CRC-16
(CCITT-FALSE, XMODEM, ARC, MODBUS, USB, KERMIT, DNP, DECT).

**Следствие:** для H4 (патч `.0ba`) сначала придётся отдельной задачей
восстановить алгоритм `$CHECKSUMME` и схему check-символа `$`-директив.
Без этого модифицированный образ не будет принят. Это конкретная, ограниченная
по объёму задача (14 известных пар «файл → checksum» дают хорошую проверяемую
базу), но её нужно запланировать.

### 4.7. Карта Ident-заголовка (`0xF80000`) — для логики выбора образа

Снято по всем 13 `.0pa`:

| Смещение | Поле | Наблюдение |
|---|---|---|
| `+0x00` | SW-ID, 12 байт (×3) | напр. `0102JU0F1F0S` |
| `+0x26` | HW-NR в BCD (×3) | `09 21 33 08` = `9213308` — **совпадает с именем файла** |
| `+0x3B` | дискриминатор семейства | **DKOML2 = `0xE0`**; HKOML2 = `0xC0`/`0xC1`/`0xC2`/`0xC3` |
| `+0x42` | поколение | `0x08` у всех DKOML2 и ранних HKOML2; **`0x09`** у `9260849A`, `9280355A`, `9283869A`, `9316169A` |
| `+0x38` | не выяснено | значения `0x6B`, `0x01`, `0x11` |

Это даёт приложению надёжный **предохранитель**: сверять семейство (`+0x3B`)
и HW-NR (`+0x26`) перед любой записью. Кросс-прошивка семейств недопустима.

## 5. Поверхность атаки: что именно эксплуатировать

Гипотезы упорядочены по отношению «шансы / стоимость проверки».

### 5.0. Развилка, которая определяет выбор пути: куда попадает правка

Прежде чем выбирать способ обхода, надо понять, **в какую область попадает
то, что мы хотим изменить**. От этого зависит, нужен ли вообще обход подписи.

| Что меняем | Где лежит | Реалистичный путь |
|---|---|---|
| Калибровки, параметры, кодировочные значения | `NVRAM` (сегмент `0x03`), кодировочные блоки | запись **без подписи** — прецедент уже есть: `STEUERN_ANPASSEN_ACC_KENNLINIE_SVDO`, `STEUERN_ANPASSEN_LCD_KENNLINIE_SVDO`, `C_C_SCHREIBEN` |
| Таблицы данных, знакогенератор, шрифты, Ident | область данных приложения `0xF80000–0xF9BFFF` | если диапазон **не покрыт** подписью → **H2** |
| Логика отрисовки, поведение | код приложения `0xF9C000+` | почти наверняка покрыт → **H2** через подмену таблицы диапазонов либо **H4** (патч загрузчика) |

Практический вывод: если задача сводится к калибровкам — возможно, **никакой
обход подписи не нужен вообще**, достаточно `SPEICHER_SCHREIBEN`/кодировочных
джобов. Если правится код — нужен именно тот класс атаки, которым работают
`xHP`/`MHD`.

### 5.0.1. ★ Что из заявленной цели достижимо БЕЗ обхода подписи

Это важный вывод для планирования: **часть цели решается сегодня, штатными
средствами**, и её не надо тащить в проект с эксплойтом.

**(а) Вывод 8 передач — вероятно, уже есть в заводском софте.**
По [BMW_KOMBI_PL2_RESEARCH.md](BMW_KOMBI_PL2_RESEARCH.md) § 5, знакогенератор и
CAN-декодер приборки были обновлены до версий **`D1..D8`, `S1..S8`, `M1..M8`**
именно в кодировочном индексе **`C09`** — то есть **8 передач в C09 уже
поддерживаются заводом**. Для свапа на 8HP может оказаться достаточно:

1. взять плату **поколения `0102`** (дискриминатор `0xF80042` = `0x09`):
   HW `9280355`, `9283869`, `9316169`, `4256458` для High и `9283868`,
   `9316168`, `4256458` для Low;
2. залить штатный **C09** через WinKFP — образ подписан BMW, подпись проходит;
3. до-кодировать NCS Expert по FA автомобиля.

Никакого эксплойта, никакой кастомной прошивки. На платах поколения `0101`
(C08 и ниже) этот путь закрыт проверкой `COAPI-2041: Wrong Hardware number` —
там уже потребуется обход.

**(б) Часть «показателей» — это калибровки и кодирование.** Калибровочные джобы
`STEUERN_ANPASSEN_ACC_KENNLINIE_SVDO` / `..._LCD_...` пишут в NVRAM **без
подписи**, а `C_C_SCHREIBEN` — штатный кодировочный механизм. Всё, что
выражается параметрами, делается без эксплойта.

**(в) Обход подписи нужен только для того, чего нет ни в одном заводском
билде** — прежде всего для полностью настраиваемой матрицы «любой показатель в
любую строку дисплея». Это новая логика в области кода.

### 5.0.2. Что цель «генератор прошивки» означает технически

Это самое важное следствие для архитектуры, и его надо учесть заранее:
**каждый HW-вариант — отдельно скомпилированный билд**, побайтовый diff между
ними даёт ~80 % различий (`HANDOFF.md`, факт №4). Значит:

* «одного патча на все приборки» быть не может — генератор обязан работать
  **по каждой версии отдельно**;
* следовательно, генератор — это прежде всего система **поиска одной и той же
  структуры в разных билдах**, а не система применения патча;
* фундамент для этого в проекте **уже есть**: `f2mc_cfg.py` (рекурсивный
  дизассемблер), `f2mc_compare.py` (структурное сравнение с сопоставлением по
  мнемоническим сигнатурам), `f2mc_family.py`, `f2mc_pairdiff.py`. Именно они
  решают задачу «найти таблицу X в билде Y».

Практический вывод: первая версия генератора должна быть **не про патчи, а про
стабильную адресацию** — уметь для любой из ~13 версий найти: таблицу символов,
таблицу атрибутов стиля, таблицы слотов дисплея, точки входа отрисовки.
Патч — уже следствие.

### H1. Чтение защищённой области штатным сервисом памяти — **проверить первым**

**✅ Всё необходимое теперь известно** (после разбора `komb87.prg`,
см. `KOMB87_SGBD_FINDINGS.md`). Это уже не «надо разобраться», а готовый к
выполнению эксперимент.

| Параметр | Значение |
|---|---|
| Джоб | `SPEICHER_LESEN(SEGMENT, ADRESSE, ANZAHL)` |
| Служба | **`$23` ReadMemoryByAddress** |
| `SEGMENT` | строка **`"FLASH"`** → внутренний Flash, код `0x06` (`"FLASHX"` = `0x09`, внешний) |
| `ADRESSE` | `0xFFC000` (диапазон `0x000000–0xFFFFFF`) |
| `ANZAHL` | до **254** за вызов → читать в цикле |

Если `"FLASH"` отдаёт `0xFFC000–0xFFFFFF`, мы получаем **дамп загрузчика по
D-CAN, не разбирая щиток**. Симметрично `SPEICHER_SCHREIBEN` — это **`$3D`
WriteMemoryByAddress** с теми же аргументами, и он **не входит** в группу
«Firmware/Flash» с challenge-response. Если ЭБУ разрешает `$3D` в сегменте
`FLASH` — задача решается вообще без эксплойта.

Порядок эксперимента (от безопасного к рискованному):
1. Чтение `"FLASH"` по `0xFFC000` — безопасно, ничего не меняет.
2. Чтение «дырки» `0xFB9FF0–0xFBBFFF` (см. H2) — безопасно.
3. Запись `$3D` сначала в **`NVRAM`** (`0x03`) на безобидный адрес —
   проверяем, есть ли вообще запись без аутентификации.
4. Только потом — запись в `FLASH`.

**Риск:** `SPEICHER_SCHREIBEN` в сегменте `FLASH` может быть заблокирован
проверкой сегмента на стороне ЭБУ. Тогда остаётся только чтение.

**Важно:** телетрамму собирает сам SGBD, поэтому на этом шаге **не нужно
писать транспорт** — достаточно вызвать джоб через EDIABAS/`api32`/`ediabasx`.
Это часы работы вместо недель (§ 7.1).

### H2. Атака «непокрытый диапазон» (в стиле MSD80) — **приоритет №2, ключи не нужны**

Публично документированный и **промышленно применяемый** класс атаки на BMW
(MSD80/MSD81, мотор N54 — так работают все коммерческие флешеры: MHD, COBB,
OpenFlash):

1. Подписей **две** — отдельно на софт и на калибровку, и подпись покрывает
   **не весь образ**, а только диапазоны из **таблицы** (пример из разбора:
   `80020000–8003FFFF`, `80040000–80053DFF`, `80080000–801FFC3F`).
2. **Сама таблица диапазонов лежит в ЭБУ и подписью НЕ покрыта.**
3. Атака: патч кладётся в непроверяемый диапазон → оригинал копируется в
   свободную память → таблица правится так, чтобы проверка смотрела на
   оригинал → **подпись проходит**, а исполняется патченая версия.

Автор разбора формулирует переносимость прямо: *«Could possibly work anywhere
that the RSA table isn't covered by the signature itself»*.
Источник: [SpoolStreet, «Technical — RSA Bypass Explained»](https://spoolstreet.com/threads/rsa-bypass-explained.9111/).

**Почему это применимо к нам.** В MS45 `FLASH_SIGNATUR_PRUEFEN` вызывается с
аргументами `Daten;64` / `Programm;64` — то есть проверяемые диапазоны
**параметризованы**, и «подпись на всё» не гарантирована. Имена джобов у KOMBI
те же.

**Кандидат на «карман» — `0xFB9FF0–0xFBBFFF` (8 208 байт).** Проверено:
этот диапазон **не пишет ни один** из 14 файлов (`.0pa` и `.0ba`); он лежит
ровно между концом блока flash-рутин и началом блока приложения. Гипотеза:
исключён из стирания/записи намеренно, чтобы рутины программирования не
затирали себя. Если он ещё и не покрыт подписью — это готовый «карман».

Что проверить: (1) какие диапазоны покрывает подпись; (2) входит ли в них
`0xFB9FF0–0xFBBFFF`; (3) стирается ли он при `NG_FLASH_LOESCHEN`; (4) размер
проверяемых блоков — косвенно по `FLASH_SIGNATURTESTZEIT` (джоб
`FLASH_ZEITEN_LESEN` даст реальное значение и подскажет порядок ключа).

Отдельный, более слабый прецедент: калибровочные джобы
`STEUERN_ANPASSEN_ACC_KENNLINIE_SVDO` /
`STEUERN_ANPASSEN_LCD_KENNLINIE_SVDO` пишут в NVRAM **без подписи** — это
другая память, но сам факт «запись без подписи существует» установлен.

### H3. Дамп защищённой области программатором (резервный путь)

Если H1 не работает: снять щиток, перевести MB90F395HA в режим
**Fujitsu standard serial on-board programming** (выводы режима + линии
`SIN`/`SOT`/`RST`) и снять дамп программатором **Fujitsu Flash Programmer
AF2xx**. Дороже по времени, но даёт **гарантированный** результат и заодно
полный 512-КБ дамп. Это единственный путь, не зависящий от того, реализован ли H1.

⚠️ **Важная поправка к `BMW_KOMBI_PL2_RESEARCH.md`:** утверждение, что для
этого подойдут VVDI Prog / Orange5 / UPA-USB, **источником не подтверждено**.
Более того, в профильной теме
([otomotiv-forum](https://otomotiv-forum.com/threads/mb90f395ha-chem-prochitat.101505/))
ровно про MB90F395HA сообщают, что Orange5 чип **не читает**, и советуют
Fujitsu Programmer по UART. Точные уровни режимных выводов именно для
MB90F395HA надо достать из `PCW16e.pdf` / Hardware Manual MB90390 — это
отдельная небольшая задача.

### H4. Подмена/патч ядра-программатора `.0ba` — самый перспективный

Мы владеем `.0ba` (см. § 4.3) — маленькой исполняемой программой, которую
загрузчик **штатно принимает** и которой передаёт управление. Схема атаки,
если подтвердится модель «временного ядра»:

1. Пропатчить `.0ba` (например, убрать вызов проверки подписи, либо заставить
   ядро писать в `0xFFC000+`).
2. Пересчитать `$CHECKSUMME` файла и check-символы `$`-директив
   (**алгоритм пока не воспроизведён — см. § 4.6; это обязательный
   предварительный шаг**).
3. Залить модифицированный `.0ba`, дать ядру записать наш образ, вернуть
   штатный `.0ba`.

Это ровно тот класс атаки, который публично документирован для F/G-серии BMW
(«patched BTLD» → модифицированный SWFL → вернуть оригинальный BTLD).

**Открытые вопросы:** проверяет ли загрузчик подпись самого `.0ba`; в каком
порядке ядро и приложение сосуществуют; нужна ли подпись для ядра.
Ответ даст `komb87.prg` + дамп защищённой области.

### H5. Reprogramming-режим после стирания

Классика: перевести щиток в режим программирования, стереть приложение так,
чтобы устройство осталось в мониторе (аналог «brick → bootloader mode» на
роутерах, приём с MSD80/EDC17). Тогда монитор принимает образ без проверки
приложения. Требует понимания логики `NG_FLASH_LOESCHEN` и того, что именно
проверяет монитор при старте. **Высокий риск получить кирпич** — только на
донорском щитке.

### H6. Слабость `AUTHENTISIERUNG`

**Режим теперь не надо угадывать.** Джоб `AUTHENTISIERUNG_ZUFALLSZAHL_LESEN`
(`$31` `$07` RequestForAuthentication) возвращает **и случайное число, и тип
аутентификации** — SGBD сам декодирует байт через таблицу `AUTHENTISIERUNG`
(`0x01` Simple, `0x02` Symetrisch, `0x03` Asymetrisch, `0xFF` Keine).
Один запрос на живом щитке закрывает вопрос.

**Где искать секрет:** в SGBD его **нет** — проверено поиском по
расшифрованному `komb87.prg` (нет ни `RSA`, ни `MD5`, ни блобов ключей; из
«ключевого» только `ERROR_TESTER_SERIAL_NR` и CBS-ключи `KEY1…KEY15`, это не
криптография). В `.ipo` есть строка
`AUTHENTISIERUNG_START ( SG-Schluessel ...)` — то есть **ключ передаётся в джоб
вызывающей стороной**, и кандидат на его хранение — сам `.ipo` (CABI-скрипт),
WinKFP или DLL. Для режима `Symetrisch` секрет обязан быть восстановим;
для `Asymetrisch` — приватный ключ у BMW, и тогда остаётся только обход.

Косвенное подтверждение схемы: `ERROR_TESTER_SERIAL_NR` — в аутентификации
участвует **серийный номер тестера**, как и в документированной MS45
(`MD5(userID ‖ serialNumber ‖ seed)`).

### 6.1. Где взять `komb87.prg` — ✅ закрыто

> **Статус:** файлы найдены на внешних дисках (4 шт., 3 различные версии),
> скопированы в `прошивки приборок/SGBD/`. Разбор — `KOMB87_SGBD_FINDINGS.md`.
> Раздел ниже сохранён как справка «где искать такие файлы».

`komb87.prg` — это **PC-файл**, а не содержимое приборки. Это SGBD
(Steuergerätebeschreibungsdatei): скомпилированное описание диагностических
джобов ЭБУ для EDIABAS. **В щитке его нет и быть не может** — программатор
даёт дамп флеша (прошивку), а SGBD приходит с софтом. Это два разных артефакта:

| Артефакт | Где живёт | Как добыть |
|---|---|---|
| `komb87.prg` (SGBD) | на PC, в составе ПО | из SP-Daten / BMW Standard Tools — **без железа** |
| Загрузчик `0xFFC000+` (прошивка) | внутри MB90F395HA | только из железа (§ 5, H1/H3) |

**Где искать на машине с BMW Standard Tools:**

```
C:\EDIABAS\Ecu\komb87.prg
C:\EC-APPS\EDIABAS\Ecu\komb87.prg
<INPA>\EDIABAS\Ecu\komb87.prg
<SP-Daten>\E89\ecu\komb87.prg      (или ...\BASE\ecu\)
```

Именно эти пути перебирает `BimmerDaten` (`inpa_parser.py`, `_detect_ecu_path`),
так что поиск можно не изобретать.

**Версия не критична.** Файл не привязан ни к VIN, ни к конкретной машине —
он одинаков для всех E9x. Проект использовал SP-Daten E89 **v69.0** (см. шапку
`KOMB87_JOBS.md` и `docs/diag-jobs.md`); подойдёт любой свежий пакет E-series,
где есть `ecu/KOMB87.prg` — в сообществе ходят, например,
[v74.0 для всех E-series](https://carmasters.org/topic/74737-делюсь-sp-daten-v740-для-всех-bmw-e-series/)
и [готовые SP-Daten-пакеты](https://binunlock.com/resources/sp-daten-data-packages-for-e-f-g-series-ista-ncs-winkfp-ready.250/).
SGBD-файлы — собственность BMW, распространение пакетов юридически серая зона
(см. § 9, п. 5).

**Инструменты для разбора уже готовы** — как только файл появится:

1. `BimmerDaten/decoderPrg.py` — контейнер SGBD (заголовок `0x9C`, тело
   XOR `0xF7`) → метаданные, список джобов, байткод. Именно им получен
   `KOMB87_JOBS.md`.
2. `_research/ediabasx` — **полный справочник BEST/2 VM**:
   `docs/sgbd-format.md` (структура контейнера, сигнатура `_EDIABAS_OBJECT`),
   `docs/vm-opcode-reference.md`, `docs/vm-opcode-handlers.md`,
   `docs/vm-reference.md`. Это то, чего не хватало `decoderPrg.py` для
   настоящего дизассемблирования байткода `AUTHENTISIERUNG_START` и
   `SPEICHER_LESEN`.

⚠️ Важно для ожиданий: SGBD — это **байткод, исполняемый на PC**. Он даёт
точные телеграммы (сервис + ID + данные) и параметры `PABD`, но **не содержит
реализации криптографии**: для симметричного режима ключ/алгоритм могут быть
в нём или в DLL, для асимметричного секрет вообще в ЭБУ.

## 7. Архитектура приложения

### 7.1. Ключевой факт: CAN делает сам кабель

Транспорт D-CAN/ISO-TP реализован **в прошивке кабеля K+DCAN**, а не в хосте.
На PC виден COM-порт; в режиме D-CAN хост отправляет **ту же телеграмму
BMW-FAST, что и на K-линии**, только на **115200 8N1**. Подтверждено кодом
`EdiabasLib` (`EdInterfaceObd.cs`): концепт `0x0110` (D-CAN) → `baudRate=115200`,
`parity=None`, `ParTransmitFunc = TransBmwFast`, запись прямо в `SerialPort`.
Класса `EdInterfaceDcan` не существует — D-CAN это «концепт» внутри
`EdInterfaceObd.cs`; CAN-обмен нужен только для «умных» адаптеров
(`EdCustomAdapterCommon.CreateCanTelegram`) или настоящей CAN-шины.

**Практическое следствие:** «свой D-CAN-стек» — это не CAN-контроллер и не
ISO-TP, а **~300–400 строк**: кадрирование BMW-FAST + тайминги + опрос
адаптера. Это радикально меняет оценку варианта (a).

| Вариант | Плюсы | Минусы |
|---|---|---|
| **(a) Свой транспорт на Python (`pyserial`)** | ~300–400 строк; кроссплатформенно; слой нужен в любом случае как логгер и «второе мнение» | прошивку на голом KWP2000 не воспроизвести (§ 2) |
| **(b) `EdiabasLib` (C#/.NET)** | есть интерпретатор BEST/2 → `FLASH_*` / `AUTHENTISIERUNG_*` работают «как у BMW» | **GPL-3.0** (заражает закрытый продукт); нужен .NET (pythonnet / sidecar) |
| **(c) Обёртка над EDIABAS / `api32.dll`** | минимальный риск, штатные джобы «из коробки» | Windows-only; нужен **32-битный Python**; batch-режим Tool32 документально не подтверждён → shell-out ненадёжен |

**Вердикт:** для чтения и актуации (разведка H1/H2) — **(a)**: быстро и
безопасно, и слой всё равно нужен как логгер. Для **прошивки** — **(b)** (если
продукт открытый/внутренний) или **(c)**; вариант (a) «в одиночку» для
прошивки — только при готовности к долгому реверсу SGBD и наличии аппаратного
восстановления.

**Важно:** прошивка — это оркестрация ~15 джобов двух SGBD с проверками
статуса, challenge-response и подписью. «erase + write» на голом KWP2000 её
**не заменяет** — это ещё один аргумент не писать flash-логику с нуля.

### 7.1.1. Байтовый формат, который надо реализовать

**Телеграмма BMW-FAST** (то, что уходит в кабель):

```
короткая:   [0x80|len] [TGT] [SRC] [data...] [sum8]
длинная:    [0x80] [TGT] [SRC] [len_lo] [data...] [sum8]
len >= 0x100: [0x80] [TGT] [SRC] [0x00] [len_hi] [len_lo] [data...] [sum8]
```

- `SRC` = адрес тестера = **`0xF1`**; `TGT` = адрес ЭБУ (в SGBD заглушка `$FF`).
- Контрольная сумма — **8-битная СУММА**, **не XOR** (XOR — только DS2/KWP1281).
- Пример: `STATUS_TANKINHALT` KOMBI (`$21 0x0A`) → `82 <TGT> F1 21 0A <sum>`.
  Этот же формат независимо подтверждён локальным разбором SP-Daten
  (`bmw-e90-can-display/docs/diag-jobs.md`).

**CAN-адресация:** запрос — всегда `0x600|0xF1 = 0x6F1`; ответ —
`0x600|адрес_ЭБУ` (ЭБУ `0x12` → ответ `0x612`). Адрес ЭБУ передаётся
в payload, то есть используется ISO-TP **extended addressing**.
Функциональный `0x6F0`/`0x7DF` для BMW D-CAN в коде **не найден**.

**Опрос адаптера** (телеграммы на «виртуальный ЭБУ `0xF1`», ответ = эхо + payload):

| Команда | Смысл ответа |
|---|---|
| `82 F1 F1 FE FE sum` | `resp[4]` = зажигание |
| `82 F1 F1 FD FD sum` | `resp[4..5]` = adapterType, `resp[6..7]` = версия |
| `82 F1 F1 FB FB sum` | `resp[4..11]` = серийный номер |
| `82 F1 F1 FC FC sum` | `resp[4]` = напряжение ×0.1 В |

**Инициализация в D-CAN:** отдельной «магической» последовательности нет —
открыть **115200 8N1**, поднять DTR/RTS, слать BMW-FAST с `TGT` = адрес ЭБУ;
кабель сам делает CAN. (Для K-line предварительно пишется baud/parity/флаги
через adapter-telegram — на E9x после ~03/2007 не нужно.)

**Подводные камни** (всё подтверждено кодом): эхо своей посылки приходит
перед ответом и сверяется байт-в-байт; DLC всегда 8 с добивкой `0x00`;
ответ `0x78` (response pending, таймаут 5000 мс, 2 повтора) — **критично при
стирании флеша**; `TesterPresent 0x3E` в фоновом потоке; тайминги
W1–W5/P1–P4; для FTDI — **latency timer = 1 мс**, иначе таймауты.

**Питание при прошивке:** внешнее ЗУ, зажигание включено, двигатель выключен,
держать **≥ 13.0–13.5 В** (вендор ЗУ для BMW указывает 14.2 В) всю процедуру,
не прерывать.

**Полезное предусловие:** напряжение бортсети KOMBI отдаёт сама
(`STATUS_KLEMMENSPANNUNG`, `$21 0x21`, мВ) — а адаптер меряет его ещё и сам
(`82 F1 F1 FC FC`).

**Осталось не выяснить:** диагностический адрес KOMB87 (берётся из
`ECU_ADR_*` в SGBD или задаётся джобом `SetEcuAdr`) — читается из вашего
SP-Daten; измеренная пропускная способность (оценка: ISO-TP даёт 6–7 байт на
consecutive frame → реально **5–25 КБ/с**, образ ~256–260 КБ → единицы минут
на всё вместе).

### 7.2. Целевая архитектура

```
┌────────────────────────────────────────────────────────┐
│ CLI / GUI                                              │
├────────────────────────────────────────────────────────┤
│ Оркестратор сессии: EnterProgrammingMode → Auth →      │
│ Erase → Write → Verify → Reset                         │
├──────────────┬──────────────────┬──────────────────────┤
│ Транспорт    │ KWP2000          │ Работа с образами    │
│ pyserial     │ сервисы          │ .0pa/.0ba/.bin       │
│ 115200 8N1   │ $21 $23 $27 $2E  │ Intel HEX ↔ flat     │
│ BMW-FAST     │ $30 $31 $34 $36  │ карта памяти         │
│ + Tester     │ $3E $37 $11      │ Ident-заголовок      │
│   Present    │ NR78 handling    │ $CHECKSUMME          │
├──────────────┴──────────────────┴──────────────────────┤
│ Безопасность: сверка семейства/HW-NR, бэкап, dry-run,  │
│ подтверждение, журнал, восстановление                  │
└────────────────────────────────────────────────────────┘
```

Обязательные модули, помимо транспорта:

- **`BmwFastCodec`** — сборка/разбор телеграмм и `sum8` (§ 7.1.1).
- **`AdapterProbe`** — детект адаптера и напряжения (таблица выше).
- **`Kwp2000Session`** — тайминги, эхо, `NR78`, фоновый `TesterPresent`.
- **Карта памяти и валидатор образа** — уже есть основа (`parse_ihex.py`):
  семейство по `+0x3B`, HW-NR по `+0x26`, поколение по `+0x42`, проверка
  границ, запрет пересечения с `0xFFC000+`.
- **Таблица «job → байты запроса»**, извлечённая офлайн из SP-Daten —
  в проекте уже есть `bmw-e90-can-display/tools/sgbd_extract.py`.
- **Бэкап перед записью**: сначала прочитать и сохранить всё, что читается
  (включая попытку `SPEICHER_LESEN`), и только потом стирать.
- **Режим `--dry-run`**: прогон всей последовательности без записи.
- **Работа с `.0ba`**: сборка/патч, пересчёт `$CHECKSUMME`.
  Основа — `parse_ihex.py` + `dump_flat.py` (плюс обратная сборка Intel HEX).
- **Декодеры**: `.prg` — переиспользовать `BimmerDaten/decoderPrg.py`;
  `.ipo` — написать (см. § 4.5).

**Для самой прошивки** слой (a) не рекомендуется в одиночку: разумная схема —
свой транспорт (a) для чтения/актуации/логирования плюс **sidecar** на (b)
или (c) для `FLASH_*`-оркестрации, по JSON-RPC. Такой паттерн уже реализован
в `ediabasx` (`ediabasx serve` + клиент).

## 9. Риски и правила безопасности

1. **Кирпич.** Необратимая ошибка в защищённой области делает щиток
   неработоспособным без программатора. Любая запись — только на донорском
   щитке до полной отработки последовательности.
2. **Питание.** Прошивка требует стабильного напряжения; при просадке —
   повреждение флеша. Обязателен источник питания/зарядное устройство,
   контроль напряжения (у KOMBI есть собственный АЦП, `STATUS_KLEMMENSPANNUNG`,
   `$21 0x21` — можно использовать как предусловие).
3. **Кросс-прошивка семейств.** HW-множества DKOML2 и HKOML2 **не
   пересекаются** (проверено по `*.DAT`/`*.HWH`), связка «железо → прошивка»
   строго 1:1. Приложение обязано жёстко валидировать семейство (`+0x3B`) и
   HW-NR (`+0x26`) до записи.
4. **Область `0xFFC000+` — не трогать.** Пока загрузчик не разобран, любая
   запись туда = гарантированный кирпич.
5. **Правовой аспект.** Обход подписи и распространение ключей BMW —
   юридически чувствительная тема. Исследование и работа со своим железом —
   одно; публикация ключей/эксплойта — другое.
6. **Обратимость.** До этапа 5 каждый шаг должен иметь путь отката: полный
   дамп до записи, сохранение оригинального `.0ba`, возможность вернуть
   штатную прошивку через WinKFP (пока загрузчик цел, штатное обновление
   остаётся рабочим).
7. **`.0ba` — единственная имеющаяся копия загрузчика.** Прежде чем что-либо
   с ней делать, снять полный дамп внешним программатором. Подтверждённого
   восстановления «кирпича» для этой приборки публично **нет**.
8. **Потеря штатной обновляемости.** Правка загрузчика может навсегда
   сломать прохождение дилерских обновлений ISTA/WinKFP, даже если щиток
   останется рабочим.
9. **Автобэкап не является образом восстановления.** В аналоге MS45
   (`nfsx`) прямо сказано: *«BMW's design doesn't include host-side firmware
   backup»*, а *«a failure mid-transfer can brick the ECU»*. Не рассчитывать
   на то, что прочитанное до записи гарантированно вернёт устройство.

## 10. Внешние источники и готовые решения

### 10.1. Прямой аналог задачи, решённый публично: BMW MS45
- [emdzej/nfsx](https://github.com/emdzej/nfsx) — реконструкция BMW NFS/WinKFP
  (TypeScript), включая [описание схемы прошивки MS45](https://raw.githubusercontent.com/emdzej/nfsx/refs/heads/main/docs/ms45-flashing.md).
- [terraphantm/MS45-Flasher](https://github.com/terraphantm/MS45-Flasher) —
  **опубликованы приватные экспоненты RSA** (`Checksums_Signatures.cs`, GPL-3.0).

Из них: доступ — RSA-512, `MD5(userID ‖ serialNumber ‖ seed)`, подпись
`c = hash^d mod n`, упаковка LSW-first (BE внутри каждого 4-байтного слова);
блоб доступа = 25-байтный заголовок EDIABAS + 64-байтная подпись + `0x03`
= **90 байт**; подпись прошивки — **отдельная** пара RSA-512, `concat`
подписанных сегментов → `MD5` → `^d mod n`; пост-флеш вызов
`FLASH_SIGNATUR_PRUEFEN` с аргументами `Daten;64` / `Programm;64`;
CRC — CRC-32/MPEG-2 (полином `0x04C11DB7`, non-reflected).

**Это архитектурный аналог, но не перенос ключей:** имена джобов в `KOMB87.prg`
совпадают, ключи для KOMBI публично не публиковались.

Экосистема того же автора, полезная как референс реализации:
[ediabasx](https://github.com/emdzej/ediabasx) — интерпретатор EDIABAS/BEST/2
с транспортами K+DCAN / J2534 / ENET;
[inpax](https://github.com/emdzej/inpax) — интерпретатор байткода INPA/IPO;
[ncsx](https://github.com/emdzej/ncsx) — NCS Expert.

⚠️ Там же описан boot-mode C167 (`0x00`/`0xC5`,
[bootmode.md](https://raw.githubusercontent.com/emdzej/nfsx/refs/heads/main/docs/bootmode.md)) —
**к нашей приборке это не относится** (§ 3.3).

### 10.2. Документированный класс атаки № 1: «непокрытый диапазон» (MSD80/81)
- [SpoolStreet, «Technical — RSA Bypass Explained»](https://spoolstreet.com/threads/rsa-bypass-explained.9111/) —
  подпись покрывает только диапазоны из таблицы, и **сама таблица не покрыта
  подписью**; так работают все коммерческие флешеры N54. Прямая цитата о
  переносимости: *«Could possibly work anywhere that the RSA table isn't covered
  by the signature itself»*. Там же: на старых ЭБУ BMW стоял RSA-512, его
  «сломали перебором», и модифицированные файлы подписывают утёкшим ключом.
  **Основа для нашего H2.**

### 10.3. Документированный класс атаки № 2: подмена загрузчика (BTLD)
- «Unlock DME/EDC flashing with E-Sys patched BTLD files»
  ([binunlock.com](https://binunlock.com/r/unlock-dme-edc-flashing-with-e-sys-patched-btld-files.72)) —
  залить патченый загрузчик (без проверки подписи) → залить модифицированный
  SWFL → вернуть оригинальный BTLD. **Контрольная сумма модифицированного
  файла всё равно должна быть корректной** (у нас это `$CHECKSUMME`, § 4.6).
  Концептуально применимо к H4.
