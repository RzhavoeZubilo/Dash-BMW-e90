## 0. Краткое резюме (TL;DR)

1. **Схема «Authentisierung + Signaturprüfung» у BMW — это единый EDIABAS-протокол с одинаковыми именами джобов на разных ЭБУ.** Для BMW **MS45** (DME E46/E60/E65) эта схема полностью реверснута публично, и **приватные ключи подписи опубликованы** в открытом GPL-проекте. Это самый близкий публичный аналог нашей задачи. ✅
2. **Публично продемонстрированный класс атаки на BMW — «подмена/патч самого загрузчика»**: залить патченый BTLD, который не проверяет подпись, затем залить модифицированную прошивку, затем вернуть оригинальный BTLD. Для F/G-серии это оформлено в пошаговую методику с библиотекой патченых BTLD. ✅
3. **Второй публично разобранный класс — «таблица проверяемых диапазонов не покрыта самой подписью»** (эксплойт MSD80/MSD81, применяется всеми коммерческими флешерами N54: MHD, COBB, OpenFlash). ✅
4. **Конкретно для BMW KOMBI (PL2) публичных эксплойтов, обходов подписи, утечек ключей и дампов загрузчика — НЕ НАЙДЕНО.** ❌
5. **Однако у нас есть то, что обычно ищут: файл загрузчика.** `H01028K_0102FH.0ba` — это штатный «Austausch-Datei Programm» образ **BSU** (загрузчик + flash-рутины), и он штатно поставляется в SP-Daten. 🔶
6. Единственная публично подтверждённая схема входа в BSL с байтом `0x00` / ответом `0xC5` — это **Infineon C167**, а **не** F2MC-16LX. Для MB90F395HA такого опубликованного протокола нет. ✅/❌

### 1.2. Про выводы MD0/MD1/MD2 и SIN0/SOT0

- ✅ **ПОДТВЕРЖДЕНО:** сводная таблица «Pins Used for Fujitsu-standard Serial On-board Programming» действительно содержит колонки с **уровнями выводов**, например для MB90F952 в сниппете поиска видно `P83/SIN1 | P86/SOT1 | P83=L,P84=L*1`. То есть **на ряде приборов F2MC-16LX режим входа задаётся не «каноническими» MD0/MD1/MD2, а обычными портами** (P8x). Это важное уточнение: **нельзя считать, что для MB90F395HA вход в режим программирования обязательно выполняется именно выводами MD0/MD1/MD2** — конкретику надо брать из Hardware Manual именно MB90F395HA.
- ✅ **ПОДТВЕРЖДЕНО:** линии данных — `SIN`/`SOT` (для интересующего нас семейства — `SIN0`/`SOT0`).
- ❌ **НЕ НАЙДЕНО:** публичного документа, в котором были бы **точно указаны уровни выводов MD0/MD1/MD2 именно для MB90F395HA / MB90390**. Аппноуты Fujitsu/Infineon по этому вопросу существуют, но **доступны только в виде PDF, а мой инструментарий в этой сессии PDF не читает** (см. «Ограничения метода» в конце). Это проверяемая и закрываемая задача для parent-агента: скачать `PCW16e.pdf` и Hardware Manual MB90390, найти строку `MB90F395` в таблице и зафиксировать уровни.

### 1.3. Про «байт 0x00» и «0x0D» — критично важное разделение

В постановке задачи смешаны два совершенно разных МК:

**Infineon C167 (MS42/MS43/ME7.x, Bosch):** здесь действительно есть **mask-ROM Bootstrap Loader (BSL)**, и его протокол входа опубликован и разобран. ✅ ([nfsx docs/bootmode.md](https://raw.githubusercontent.com/emdzej/nfsx/refs/heads/main/docs/bootmode.md)):

- Вход: вывод `BOOT` в логический `0` на момент сброса → МК входит в BSL, слушает `ASC0`.
- Формат: **8N1**, скорость выбирает хост, BSL **авто-бод**.
- Шаг 2: хост посылает **`0x00`** — это эталон авто-бода: битовая картина `0 00000000 1` (старт + 8 нулей + стоп) даёт BSL отмерить ровно 9 битовых периодов.
- Шаг 3: МК отвечает **идентификационным байтом**: `0xC5` на C167CR (MS42/MS43), `0xAA` на части C167 (ME7/Simos 3.x).
- Шаг 4: загрузка **ровно 32 байт** первичного загрузчика (ограничение кремния), затем он стягивает вторичный загрузчик.
- Шаг 6: «ready»-байт специфичен для вторичного загрузчика: MiniMon — `0x01`/`0x03`, JMG-блоб — `0xC5`.
- Дальше — произвольный протокол, определяемый вторичным загрузчиком (например, набор команд MiniMon: `0x82 C_WRITE_WORD`, `0xCD C_READ_WORD`, `0x84 C_WRITE_BLOCK`, `0x85 C_READ_BLOCK`, `0x9F C_CALL_FUNCTION`, `0x33 C_GETCHECKSUM`; ACK `0xAA` / `0xEA`).

**Fujitsu F2MC-16LX (наш MB90F395HA):**
- ❌ **НЕ НАЙДЕНО** ничего похожего: ни опубликованного байта синхронизации, ни команды `0x0D`, ни «BSL»-протокола с идентификационным байтом. Утверждение о «специальных командах `0x00`/`0x0D`» для F2MC-16LX **публичными источниками не подтверждается**. Похоже, что это перенос фактуры C167 на F2MC.
- ⚠️ **УТВЕРЖДАЕТСЯ (важная негативная находка):** на профильном форуме чип-тюнеров задан ровно наш вопрос — *«подскажите чем дешевым можно прочитать MB90F395HA? смотрю в сторону Orange 5, но есть жалобы что не читает»* — и единственный ответ: *«Можно попробовать **Fujitsu Flash Programmer** (или еще какой софт есть) по uart»*. То есть **дешёвые универсальные программаторы (Orange5) с MB90F395HA публично не подтверждены**, а рекомендуемый путь — штатный UART-программатор Fujitsu. ([otomotiv-forum.com](https://otomotiv-forum.com/threads/mb90f395ha-chem-prochitat.101505/))

### 1.4. Где физически живёт загрузчик KOMBI — 🔶 НАШ АНАЛИЗ (публично не опубликовано)

Это, пожалуй, самый ценный результат нашего локального разбора, потому что он меняет постановку задачи.

**Разбор реальных файлов из SP-Daten (E89 v69.0) в рабочей папке:**

| Файл | Покрываемые адреса | Размер |
|---|---|---|
| `HKOML2/9280355A.0pa` | **Block 0:** `0xF80000–0xFB9FEF`; **Block 1:** `0xFBC000–0xFFBFEF` | 237 504 + 262 064 Б |
| `DKOML2/9213308A.0pa` | **Block 0:** `0x000000–0x00EFEF`; **Block 1:** `0xF80000–0xFB9FEF`; **Block 2:** `0xFBC000–0xFFBFEF` | 61 424 + 237 504 + 232 400 Б |
| **`DKOML2/H01028K_0102FH.0ba`** | **Block 1:** `0xF80000–0xF86A4F`; **Block 2:** `0xFFBF50–0xFFBFEF` | **25 120 Б** + 160 Б |

**Выводы:**

1. 🔶 **Файл `.0ba` — это и есть образ загрузчика (BSU).** Его заголовок в комментариях: `;Austausch-Datei Programm`, `$REFERENZ 01028K0F130S H`, **`$BSU_REFERENZ_NEW 0102FH O`**, **`$BSUTIME 0x0005 G`**. `BSU` = обновление базового ПО (загрузчика); `BSU_REFERENZ_NEW 0102FH` — референс новой BSU. ✅/🔶
2. 🔶 **Загрузчик расположен по адресам `0xF80000–0xF86A4F`** (~25 КБ). Это и есть та самая «защищённая область», которую, по постановке задачи, `.0pa` не перезаписывает.
3. ❌ **НО: `.0pa` формально перекрывает `0xF80000–0xFB9FEF`, то есть адресно заходит на область загрузчика.** При этом содержимое по `0xF80000` в `.0pa` и `.0ba` **РАЗНОЕ**:
   - `.0pa`: `0102JU0F1C0S…`, по смещению `0xF80043` — байт **`0x09`**;
   - `.0ba`: `01028K0F130S…`, по смещению `0xF80043` — байт **`0x08`**.

   То есть `.0pa` **не является копией загрузчика**; в этом адресном окне у `.0pa` своя (прикладная) структура. Практический вывод: **решение о том, что пишется, принимает не файл, а flash-job** — он раскладывает образ на «Datenblöcke» и пишет по списку (в `.ipo` есть строки `Anzahl Datenbloecke`, `Block(`, `) Startadressse =`, `Gesamtanzahl Bytes=`). Это надо проверять по списку блоков, а не по диапазону HEX-файла.
4. 🔶 **Две области не пишутся НИ ОДНИМ файлом:**
   - **`0xFB9FF0–0xFBBFFF`** — 8 208 байт;
   - **`0xFFBFF0–0xFFFFFF`** — 16 400 байт.
   
   Особенно интересна первая: она расположена **непосредственно за** «flash-рутинами», на которые ссылается таблица (см. п. 5), и перед началом приложения (`0xFBC000`). Гипотеза (🔶, требует проверки): это область, **намеренно исключённая из стирания/записи**, чтобы flash-рутины могли работать, не стирая себя. Если она **также исключена из проверки подписи** — это готовый «карман» для инъекции кода в стиле эксплойта MSD80 (§2.3). Это самая перспективная точка для дальнейшего реверса.
5. 🔶 **Блок `0xFFBF50–0xFFBFEF` (160 байт) — это таблица 32-битных указателей (40 записей, little-endian), которую пишут и `.0ba`, и `.0pa`:**
   - в **`.0ba`** ВСЕ записи = `0x00F869D7` (заглушка внутри загрузчика), одна запись = `0x00F869D1`;
   - в **`.0pa`** — реальные адреса: `0x00FB9FC8`, `0x00FB9FC2`, `0x00FDA0AD`, `0x00FDA0BF`, `0x00FDA0D1`, `0x00FDA0E3`, `0x00FDA0F5`, `0x00FDA107`, `0x00FDA119`, `0x00FDA12B`, `0x00FDA13D`.
   
   По смыслу это **диспетчерская таблица NG_\*-рутин** (в KOMBI это `NG_FLASH_LOESCHEN`, `NG_FLASH_SCHREIBEN_*`, `NG_SIGNATUR_PRUEFEN`, `NG_AUTHENTISIERUNG_START`). Определить, какая запись какой рутине соответствует, — приоритет №1 для реверса: именно `NG_SIGNATUR_PRUEFEN` и есть наш блокер.

### 1.5. Про «Flashprogrammierroutine» внутри KOMBI — что мы знаем точно

🔶 **НАШ АНАЛИЗ** списка джобов `komb87.prg` (полный список из 133 джобов зафиксирован в `прошивки приборок/KOMB87_JOBS.md`) показывает **три независимых класса**:

1. **Кодирование NCS Expert** — `C_C_LESEN` / `C_C_SCHREIBEN` / `C_C_AUFTRAG`, `C_CHECKSUMME`. Работают через KWP2000 `$22`/`$2E` по диапазону идентификаторов `$3000–$3EFF`. **Контрольная сумма, а не криптоподпись.**
2. **`SPEICHER_LESEN` / `SPEICHER_SCHREIBEN`** — универсальный доступ по сегменту+адресу (сегменты `ROMI`, `ROMX`, `NVRAM`, `RAMIS`, `RAMXX`, `FLASH`, `UIFM`, `VODM`, `FLASHX`, `RAMIL`). Сюда же — калибровочные джобы `STEUERN_ANPASSEN_ACC_KENNLINIE_SVDO` / `STEUERN_ANPASSEN_LCD_KENNLINIE_SVDO` (пишут в NVRAM **без подписи**).
3. **Firmware/Flash** — `AUTHENTISIERUNG_*`, `FLASH_LOESCHEN`, `FLASH_SCHREIBEN*`, `FLASH_SIGNATUR_PRUEFEN`. **Единственная группа с challenge-response и проверкой криптоподписи.**

Это подтверждает: **проверка подписи относится только к перепрошивке приложения, а не к кодированию/калибровкам.**

### 1.6. Есть ли на MB90F395HA защита секторов (и значит ли это, что загрузчик нельзя стереть)?

✅ **ПОДТВЕРЖДЕНО:** F2MC-16LX поддерживает **функцию защиты секторов Flash** (Infineon KB «How to use well the sector protecting function»). Это стандартный механизм, которым можно защитить область загрузчика от стирания/записи из приложения.
❌ **НЕ НАЙДЕНО:** публичных данных о том, какие именно сектора MB90F395HA в KOMBI защищены.
🔶 **НАШ АНАЛИЗ (косвенно):** то, что BMW штатно поставляет и применяет `.0ba` (перезапись `0xF80000–0xF86A4F`), означает, что **загрузчик в этом МК перезаписываем** — то есть, в отличие от C167, где BSL в mask-ROM и «неубиваем», здесь загрузчик **может быть изменён тем же механизмом, что и приложение**. Это принципиально важно для стратегии (§7).

## 2. Вопрос 2. Публичные эксплойты, обходы и слабости проверки подписи BMW

### 2.1. ✅ ПОДТВЕРЖДЕНО: BMW MS45 — схема полностью реверснута, приватные ключи опубликованы

Это самый близкий к нам публичный аналог, и он **документирован на уровне байтов**.

Проект **`emdzej/nfsx`** — открытая реконструкция BMW NFS/WinKFP на TypeScript ([github.com/emdzej/nfsx](https://github.com/emdzej/nfsx)). Документ [docs/ms45-flashing.md](https://raw.githubusercontent.com/emdzej/nfsx/refs/heads/main/docs/ms45-flashing.md) описывает схему для MS45.0/MS45.1:

- **Джобы (те же имена, что в нашем `KOMB87.prg`!):** `seriennummer_lesen` → `authentisierung_zufallszahl_lesen` (аргумент `"3;0x<UUUU>"`, уровень 3) → `authentisierung_start` (бинарный блоб 90 байт) → `flash_loeschen` → `flash_schreiben_adresse` → `flash_schreiben` → `flash_schreiben_ende` → **`FLASH_SIGNATUR_PRUEFEN`** (аргументы `Daten;64` или `Programm;64`) → `STEUERGERAETE_RESET`.
- **Аутентификация (security access level 3):**
  - `hash = MD5(userID || serialNumber || seed)`;
  - `c = hash-as-LE-BigInt ^ d mod n` — **RSA-512** (модуль влезает в 64 байта);
  - упаковка: `repack(c)` — **порядок байт внутри каждого 4-байтного слова BIG-endian, слова — от младшего**;
  - сообщение = `25-байтный заголовок EDIABAS || 64-байтная подпись || 0x03` = **90 байт**.
- **Подпись прошивки:** **отдельная пара RSA-512** (`FIRMWARE_MODULUS` / `FIRMWARE_PRIVATE_EXPONENT`), та же упаковка. `concat` всех байт подписанных сегментов → `MD5` → `^d mod n` → 64 байта по фиксированному смещению (`0x174` для tune-блоба, `0x60074` для program-блоба).
- **Приватные экспоненты опубликованы** в проекте **`terraphantm/MS45-Flasher`** (GPL-3.0), файл `Checksums_Signatures.cs`; `nfsx` их переиспользует ([github.com/terraphantm/MS45-Flasher](https://github.com/terraphantm/MS45-Flasher)).
- Контрольные суммы — **CRC-32/MPEG-2** (полином `0x04C11DB7`, non-reflected, без финального XOR), начальное значение берётся из заголовка блоба.

⚠️ **Осторожно с внутренним противоречием источника:** README `nfsx` в одном месте называет ключи «RSA-1024», тогда как детальная спецификация `docs/ms45-flashing.md` последовательно говорит **RSA-512** и указывает размер блока 64 байта (§3.1, §5). Правильнее доверять детальной спецификации — **RSA-512**; в README ошибка/разнобой.

### 2.2. ✅ ПОДТВЕРЖДЕНО: эксплойт MSD80/MSD81 — «таблица проверяемых диапазонов не покрыта подписью»

Разобрано на SpoolStreet участником `carabuser` в теме **«Technical — RSA Bypass Explained»** ([spoolstreet.com/threads/rsa-bypass-explained.9111](https://spoolstreet.com/threads/rsa-bypass-explained.9111/)). Это ровно то, что используют **все** коммерческие флешеры N54 (MHD, COBB, OpenFlash):

1. **Подписи две** — отдельно на софт и отдельно на калибровку. Подпись покрывает **не весь bin**, а только диапазоны, перечисленные в **таблице** (пример из темы: `80020000–8003FFFF`, `80040000–80053DFF`, `80080000–801FFC3F`). Не покрыты, в частности, области, которые разработчик считал «пустыми».
2. **Сама таблица диапазонов живёт в ECU-SW и подписью не покрыта.**
3. **Атака:**
   - берём CBOOT (загрузчик, который выполняет проверку подписи), патчим в нём ветку проверки — получаем «CBOOT без проверки»;
   - патченый CBOOT кладём в область `80040000–80053DFF`, откуда он будет скопирован в CBOOT **после** успешной проверки подписи;
   - **оригинальный, немодифицированный** CBOOT кладём в свободную память (`0x80053E00–0x8007FFFF`);
   - правим **таблицу диапазонов** так, чтобы она указывала на копии оригинального кода, а не на патченые области;
   - → проверка подписи проходит (все проверяемые байты идентичны исходным), а в CBOOT записывается патченая версия → **ЭБУ разблокирован навсегда**.
4. Прямая цитата из темы о переносимости: *«Could possibly work anywhere that the RSA table isn't covered by the signature itself.»*
5. Там же подтверждено: **на старых ЭБУ BMW использовался RSA-512, и его взломали перебором**, после чего подписывают модифицированные файлы утёкшим приватным ключом (MSV DME, старые TCU АКПП). На MSD80/81 BMW перешла на **RSA-1024**, чтобы это стало вычислительно невозможным. ✅

**Почему это важно для нас.** Наш блокер — «любое изменение байта валит проверку». Если в загрузчике KOMBI список проверяемых диапазонов **сам не покрыт подписью** и лежит в изменяемой области — это самый прямой путь. А если подтвердится гипотеза из §1.4.4 про «непокрытую/непрошиваемую» область `0xFB9FF0–0xFBBFFF`, то у нас есть ещё и готовый «карман» для размещения патча — точь-в-точь как свободные области в эксплойте MSD80. 🔶

### 2.3. ✅ ПОДТВЕРЖДЕНО: патч самого загрузчика (BTLD) через E-Sys

Опубликована пошаговая методика (**BinUnlock**, «Unlock DME/EDC Flashing with E-Sys & Patched BTLD Files», 11.07.2025) с библиотекой готовых **патченых BTLD** ([binunlock.com/r/unlock-dme-edc-flashing-with-e-sys-patched-btld-files.72](https://binunlock.com/r/unlock-dme-edc-flashing-with-e-sys-patched-btld-files.72/)):

> *«Normally, E-Sys will reject any firmware (SWFL) that has been modified because the digital signature (checksum) will not match. This method works around that limitation… **1. Patched Bootloader Flash**: first, you flash a patched bootloader. This special BTLD does not perform a signature check on the main software. **2. Modified Software Flash**: with the patched bootloader active, you can now flash your modified main software. **3. Restore Original Bootloader**: finally, you re-flash the original, official bootloader. The ECU is now back in a safe state, but the modified data from your tuning file remains active.»*

Важные детали оттуда: BTLD-файлы ~75–82 КБ в формате PSdZData; первый проход BTLD может закончиться **ошибкой, и это нормально** — надо просто повторить; **контрольная сумма (CHK) модифицированного SWFL всё равно обязана быть корректной**, иначе ЭБУ не закодируется. Это платформа F/G-серии (E-Sys, PSdZData), но **принцип переносим на любую систему, где загрузчик перезаписываем** — а у нас он перезаписываем (§1.6).

## 3. Вопрос 3. Схема «Authentisierung»: SMA (asymmetrisch), SMB (symmetrisch), SMC (simple)

### 3.1. Что мы знаем из первичного артефакта (🔶 НАШ АНАЛИЗ, публично не опубликовано)

В `080100HKOML2.ipo` (скрипт `08FLASH 8.01`) присутствуют строки, задающие все три режима:

```
AUTHENTISIERUNG
Authentisierungsart : 
Asymetrisch
T_SMA
Symetrisch
T_SMB
Simple
T_SMC
Key  : 
Schluessellaenge   
NG_AUTHENTISIERUNG_START
...
, AUTHENTISIERUNG_START ( SG-Schluessel ...)
```

- ✅ **ПОДТВЕРЖДЕНО (по файлу, но файл не публичен):** ровно три режима — `Asymetrisch`=`T_SMA`, `Symetrisch`=`T_SMB`, `Simple`=`T_SMC`, и есть параметры **«Key»** и **«Schluessellaenge»** (длина ключа). То есть длина ключа — **переменный параметр**, а не константа. Это согласуется с гипотезой, что режим/длина берутся из SGBD.
- ✅ Вызов чтения случайного числа: `AUTHENTISIERUNG_ZUFALLSZAHL_LESEN (3;` — **та же схема «уровень 3», что и у MS45** (§2.1). Это сильный аргумент, что архитектура общая.
- ✅ Присутствуют параметры из SGBD: `PABD-SG_AUTHENTISIERUNG`, **`PABD-TestSchluesselAuthentisierung`**, `PABD-ProzessorTyp`, а также тайминги `FLASH_AUTHENTISIERZEIT`, `FLASH_SIGNATURTESTZEIT`, `FLASH_LOESCHZEIT`, `FLASH_RESETZEIT`.

🔶 **Ключевое наблюдение про вариант KOMBI.** Файлы `080100HKOML2.ipo` и `080101DKOML2.ipo` **имеют одинаковый размер 46 880 байт и различаются РОВНО ОДНИМ БАЙТОМ** — по смещению `0x8036` (`H` ↔ `D`), то есть только строкой типа ЭБУ `"HKOML2"` ↔ `"DKOML2"`. Всё остальное, включая логику аутентификации, идентично.

🔶 Рядом с этой строкой в пуле данных лежит запись:

```
…EE-21 Stefan Jurchen \n \x04 \n \x04 HKOML2 \n \x02\x02\x00 \x02\x05\x00 \x02\x12\x00 \x02\x01\x00 \x04 Asymetrisch \n \x04 StartDiagnose …
```

То есть **за строкой типа ЭБУ сразу следует кортеж значений (2, 5, 18, 1) и строка `Asymetrisch`**. Наиболее вероятная интерпретация: это **запись значений по умолчанию** для данного типа ЭБУ, где режим по умолчанию — **`Asymetrisch` (T_SMA)**.

⚠️ **Оговорка (обязательна):** это **вывод по структуре пула данных, а не доказательство**. В `.ipo` есть механизм «Default-Wert wird verwendet!» при невалидном значении, поэтому запись похожа на дефолт. **Реальное действующее значение приходит из SGBD** `KOMB87.prg` в параметре `PABD-SG_AUTHENTISIERUNG`. Чтобы ответить на вопрос «какой режим использует KOMBI» **окончательно, нужен разбор `komb87.prg`** — файла в рабочей папке нет (см. §9).

### 3.2. Что известно публично про алгоритмы и ключи

- ✅ **Для MS45 (не для KOMBI!) алгоритмы и ключи полностью опубликованы** — см. §2.1: `MD5`, RSA-512, две разные пары ключей (одна для security access, вторая для подписи прошивки), упаковка «LSW-first, BE внутри слова», блоб 90 байт.
- ❌ **Для KOMBI (KOMB87 / PL2): публично НЕ опубликовано ничего** — ни алгоритм, ни длина ключа, ни ключевой материал, ни то, какой из SMA/SMB/SMC реально используется. Ни в GitHub, ни на mhhauto / cartechnology / ecuconnections / digital-kaos / chipsoft, ни в русскоязычных источниках.
- ⚠️ **Перспективная, но непроверенная зацепка:** параметр **`PABD-TestSchluesselAuthentisierung`** («тестовый ключ аутентификации»). Если в `komb87.prg` он включён, может существовать штатный «тестовый ключ», принимаемый вместо боевого. Это **гипотеза**, требующая разбора SGBD; публичных упоминаний этого параметра найти не удалось.

### 3.3. Почему аутентификация и подпись — это ДВЕ РАЗНЫЕ проблемы

Важно не смешивать, иначе планирование ломается:

| | `AUTHENTISIERUNG` (challenge-response) | `NG_SIGNATUR_PRUEFEN` (подпись образа) |
|---|---|---|
| Кто проверяет | ЭБУ проверяет **тестера** | ЭБУ проверяет **свою прошивку** |
| Где секрет | **Секрет у тестера** → лежит в `KOMB87.prg` на каждой машине с ISTA/WinKFP | Секрет — **приватный ключ BMW**, нигде не лежит |
| Кто может восстановить | 🔶 Потенциально мы: секрет **обязан** быть в SGBD, т.к. аутентификация выполняется офлайн | ❌ Только BMW (или взлом/обход) |
| Последствие обхода | Разрешение **записать** | Разрешение **запустить** записанное |

🔶 Следствие: **даже полный обход `AUTHENTISIERUNG` не даёт запуска модифицированной прошивки.** Он даёт только возможность писать. Наш блокер — второй столбец.

При этом **`AUTHENTISIERUNG` полезен как средство**: если мы сможем пропускать аутентификацию, мы получим возможность **заливать в том числе модифицированный `.0ba` (BSU)**, а это уже путь из §2.3.

### 3.4. Про «оставить ЭБУ в загрузчике и писать что угодно»

- ✅ **Для C167 это работает и описано публично:** *«Bootmode bypasses DS2 entirely… There is no BMW firmware in the path, no DS2 framing, no SEED/KEY, and no region table — the full 512 KB is addressable… This is also why bootmode **recovers a bricked ECU**: even with flash erased, the BSL still answers the power-on entry sequence.»* ([nfsx docs/bootmode.md](https://raw.githubusercontent.com/emdzej/nfsx/refs/heads/main/docs/bootmode.md)). Причина — BSL в **mask-ROM**, вне прошивки.
- ❌ **Для BMW KOMBI / F2MC-16LX такого публичного результата нет.** Более того, 🔶 наш анализ (§1.6) показывает, что загрузчик KOMBI **живёт во Flash и перезаписывается** штатным `.0ba`, то есть он **не** является независимым от прошивки mask-ROM-рутиной. Значит трюк «стёрли всё → загрузчик принял произвольный код» **не переносится автоматически** и требует отдельного доказательства.
- ⚠️ Для C167 честно указано и ограничение: *«In-vehicle bootmode is not viable: the power-up sequence isn't controllable, the BOOT pin isn't exposed, and surrounding bus traffic isn't quiet.»* — то есть это **только стенд**.

**Полезное перекрёстное подтверждение:** таблица E65 (§выше) указывает, что CAN-ID **`0x1D2` = «Display gearbox data», отправитель EGS**. 🔶 Наш локальный реверс приборки HKOML2/DKOML2 независимо показал, что приборка принимает **`0x1D2`** и берёт `B1 & 0x03` как индекс стиля рамки вокруг буквы передачи. **Два независимых источника сходятся** — это подтверждает и CAN-ID, и то, что наша находка про рамку верна по механизму.

### 5.2. Стрелка температуры масла вместо эконометра — что публично известно

Это самая «рабочая» задача из списка, и она **решается без правки прошивки**:

- ✅ **Perfekt Toolbox 0.2b** заявляет *«Switch "consumption" gauge to oil-temperature function with related thresholds»* ([источник](https://binunlock.com/r/bmw-e6x-e9x-kombi-cluster-configuration-toolbox.368/)).
- ✅ Китайская тема с прямым названием **«3种方法宝马e90瞬时油耗仪表编程刷机改成机油温度表»** — «3 способа перепрограммировать/перепрошить указатель мгновенного расхода E90 в указатель температуры масла» ([a.xcar.com.cn](https://a.xcar.com.cn/bbs/thread-96090901-0.html)).
- ✅ Польская тема **«E60/E90 Tmp. oleju w zegarach zamiast momentalnego spalania»** — та же задача ([bmwklubpolska.pl](https://www.bmwklubpolska.pl/forum/topic/150018-e60e90-tmp-oleju-w-zegarach-zamiast-momentalnego-spalania/)).
- 🔶 **Наш анализ** (в `HANDOFF.md`, раздел про `STEUERN_*`) нашёл более сильный факт: **BMW сама документирует в заводском диагностическом задании**, что стрелку KVA (расход) можно подменить произвольным значением через штатный сервис KWP2000 **`$30 InputOutputControlByLocalIdentifier`**, и что **та же стрелка управляет отображением температуры масла**. Джобы: `STEUERN_TACHO`, `STEUERN_DREHZAHL`, `STEUERN_KVA`, `STEUERN_TANK`, `STEUERN_ACC_ZEIGER`, `STEUERN_VWF`. Служба `$30` по стандарту действует, пока сессия удерживается открытой → внешнее устройство, поддерживающее K-CAN/KWP2000 и удерживающее сессию, может **непрерывно перезаписывать показания существующей стрелки в реальном времени — без единой правки прошивки и без обхода `AUTHENTISIERUNG`/`FLASH_SIGNATUR_PRUEFEN`**.
  🔶 **Ограничение, зафиксированное в наших же заметках:** подтверждено **только для аналоговых стрелок**. Джобов, нацеленных на **цифровое** поле (BC-дисплей), в списке из 133 джобов не нашлось.

### 5.3. Прямой ответ на вопрос

- ❌ **НЕ НАЙДЕНО ни одного публичного проекта, который патчит бинарник прошивки KOMBI (HKOML2/DKOML2/BKOML2/KOMBL2) и заливает его обратно.** Ни кастомных шрифтов, ни кастомной графики, ни «правильного» ремапа стрелок через firmware-патч.
- ✅ Всё, что сообщество реально делает с E9x-приборкой, делается **тремя способами без правки прошивки**:
  1. **CAN-эмуляция** (veikkos и др.) — приборка остаётся заводской;
  2. **Кодирование NCS Expert** (FSW/PSW, `SG_CODIEREN`, пустой `FSW_PSW.MAN`) — параметры комплектации, включая `ZYLINDER_ZAHL`, `DZM_UMRECHNUNG`, `KVA_FAKTOR`/`KVA_MOTOR`;
  3. **Калибровочные джобы** (`SPEICHER_SCHREIBEN` / `STEUERN_ANPASSEN_*_KENNLINIE_SVDO`) — правки в NVRAM, **без подписи**.
- ⚠️ Единственная публичная «прошивочная» активность вокруг KOMBI — это **штатные обновления** (WinKFP + заводские `.0pa`), не модификации.
- **Вывод:** наша задача (кастомная прошивка KOMBI) **публично никем не решена и, судя по всему, никем публично не предпринималась**. Ниша пустая — но и опереться не на что.

### 6.2. Практический вывод: загрузчик у нас УЖЕ ЕСТЬ

🔶 **Это ключевой практический результат.** Файл `DKOML2/H01028K_0102FH.0ba` — это:

- формат: **тот же «Austausch-Datei Programm»** (Intel HEX с комментариями BMW), что и `.0pa`;
- заголовок: `$REFERENZ 01028K0F130S H`, **`$BSU_REFERENZ_NEW 0102FH O`**, **`$BSUTIME 0x0005 G`**;
- покрытие: **`0xF80000–0xF86A4F` (25 120 байт)** + **`0xFFBF50–0xFFBFEF` (160 байт — таблица указателей)**.

То есть **тот самый «защищённый регион, который .0pa не перезаписывает», у нас есть в виде официального образа.** Его можно дизассемблировать нашим `f2mc_disasm.py` / `f2mc_cfg.py` и искать:
1. реализацию проверки подписи (`NG_SIGNATUR_PRUEFEN`);
2. **таблицу проверяемых диапазонов** (§2.2) и проверить, покрыта ли она сама подписью;
3. открытый ключ (или его хеш), если проверка асимметричная — по размеру блока можно будет оценить RSA-512 vs RSA-1024;
4. реализацию `NG_AUTHENTISIERUNG_START` — и понять, где лежит секрет (в загрузчике только верификация, секрет — в SGBD).

## 7. Практические выводы для нашего проекта

### 7.1. Переформулировка задачи

Наш блокер — **не** аутентификация (она решаема: секрет лежит в `KOMB87.prg`, который есть на каждой машине с WinKFP), а **пост-флешевая проверка подписи** `NG_SIGNATUR_PRUEFEN`, выполняемая загрузчиком. Разделять эти две вещи критично (§3.3).

### 7.2. Три стратегии, упорядоченные по отношению «ожидаемые затраты / шанс успеха»

**Стратегия A (сначала проверить — низкие затраты, высокий приоритет): «непокрытый диапазон» в стиле MSD80.**
1. Взять `.0ba` (`0xF80000–0xF86A4F`) и найти в нём `NG_SIGNATUR_PRUEFEN` (адрес подскажет таблица из 40 указателей `0xFFBF50–0xFFBFEF` — надо сопоставить записи с NG-рутинами).
2. Извлечь **таблицу проверяемых диапазонов**.
3. Проверить, **покрыта ли сама таблица подписью**.
4. Если нет — реализовать атаку из §2.2: положить патч в непроверяемый регион и перенаправить таблицу. 🔶 **Кандидат №1 для «кармана» — `0xFB9FF0–0xFBBFFF` (8 208 байт), который не пишет ни один `.0pa`/`.0ba`.** Обязательно проверить, стирается ли он вообще и покрыт ли подписью.
   *Плюс стратегии: полное совпадение с уже работающим публичным приёмом на BMW; не требует ключей.*

**Стратегия B: патч загрузчика (BSU) по образцу E-Sys/BTLD.**
1. Пропатчить `.0ba` так, чтобы `NG_SIGNATUR_PRUEFEN` всегда возвращала успех (или не вызывалась).
2. Залить патченый `.0ba` → залить модифицированный `.0pa` → при желании вернуть штатный `.0ba`.
3. 🔶 **Проблема, которую надо решить:** чем проверяется сам `.0ba`? Если BSU-обновление защищено только `AUTHENTISIERUNG` (challenge-response, ключ в SGBD) — путь открыт. Если у BSU есть **своя** подпись — упираемся.
   *Плюс: трюк «вернуть оригинальный загрузчик, оставив модифицированное приложение» из §2.3 применим буквально.*

**Стратегия C: извлечь ключ из `KOMB87.prg`.**
1. Разобрать `komb87.prg` (у нас есть `decoderPrg.py` / `BimmerDis`), найти джобы `AUTHENTISIERUNG_ZUFALLSZAHL_LESEN` (@0x4390A) и `AUTHENTISIERUNG_START` (@0x446AD) — они уже доступны для дизассемблирования (зафиксировано в `HANDOFF.md`).
2. Вытащить ключевой материал и определить режим (`SMA/SMB/SMC`) и длину ключа из `PABD-SG_AUTHENTISIERUNG`.
3. ⚠️ **Ограничение:** это даст **только аутентификацию**, то есть право писать — но **не** даст пройти `NG_SIGNATUR_PRUEFEN`. Как самостоятельный путь — **недостаточно**; как «входные ворота» для стратегии B — **необходимо**.
4. Проверить параметр **`PABD-TestSchluesselAuthentisierung`** — если тестовый ключ активен, аутентификация может обходиться тривиально.

### 7.3. Что стоит сделать в первую очередь (конкретные шаги)

1. **Найти `komb87.prg`** (в рабочей папке его нет). Он есть в любом BMW Standard Tools / SP-Daten (`…/ECU/KOMB87.prg`). Без него нельзя ответить «какой режим SMA/SMB/SMC и какая длина ключа».
2. **Сопоставить 40 указателей таблицы `0xFFBF50–0xFFBFEF` с NG-рутинами.** Для этого: определить, какие `NG_*`-ID соответствуют индексам (`NG_FLASH_LOESCHEN`, `NG_AUTHENTISIERUNG_START`, `NG_SIGNATUR_PRUEFEN`, …). Это ~полдня работы и открывает обе стратегии (A и B).
3. **Дисассемблировать `0xF869D7`** (заглушка, на которую ссылается вся таблица в `.0ba`) — понять, что это: «not supported» или общий диспетчер.
4. **Проверить гипотезу `0xFB9FF0–0xFBBFFF`**: сохраняется ли содержимое при флешинге, стирается ли блок, покрыт ли подписью.
5. **Проверить секундомер подписи.** В SGBD есть параметр `FLASH_SIGNATURTESTZEIT` (джоб `FLASH_ZEITEN_LESEN`) — реальное значение на нашем щитке даст оценку вычислительной сложности проверки и косвенно подскажет порядок ключа (RSA-512 vs 1024 vs симметричная схема).
6. **Снять логику на проводе.** Один легальный прогон WinKFP с логированием EDIABAS (или sniffer на K-CAN) даст точные байты `AUTHENTISIERUNG_ZUFALLSZAHL_LESEN` (`3;0x…`), 90-байтный блоб `AUTHENTISIERUNG_START` и аргументы `NG_SIGNATUR_PRUEFEN`. Это эмпирически подтвердит или опровергнет перенос схемы MS45 (§2.1) на KOMBI.
7. **Проверить `.0da`-файлы KOMBI.** Мы разобрали `.0pa` и `.0ba`; есть ещё `.0da` (Datensatz). Возможно, там лежит отдельная сигнатурная структура (как `Daten;64` в MS45).
8. **Заглянуть в Arduino-Tacho Gang Discord** — единственный источник, где, вероятно, есть неопубликованные знания по этим щиткам.

### 7.4. Обходной путь без обхода подписи (если стратегии A–C не сработают)

🔶 BMW **сама** документирует, что стрелку KVA можно подменить через KWP2000 **`$30`**, и что **та же стрелка показывает температуру масла** (зафиксировано в наших заметках). Плюс `STEUERN_TESTBITMAP` рисует тестовую битмапу на дисплее. Это даёт частичный функционал (**аналоговые стрелки в реальном времени; тестовая графика**) **вообще без правки прошивки и без обхода `AUTHENTISIERUNG`/`FLASH_SIGNATUR_PRUEFEN`** — при условии, что внешнее устройство удерживает диагностическую сессию. **Ограничение: цифровое поле (BC-дисплей) этим не покрывается** — джобов `$30` для него в списке нет.

### 7.5. Риски

- ⚠️ `.0ba` — единственная копия загрузчика. **Перед любыми экспериментами снимите полный дамп по внешнему программатору** (иначе «кирпич» не восстановить): для F2MC-16LX путь — Fujitsu Flash Programmer по UART (§1.1), при этом Orange5 для этого чипа публично **не подтверждён** (§4.4).
- ⚠️ Автор `nfsx` прямо предупреждает: *«All write commands can brick an ECU»*, а `backup` — это **не** образ для восстановления.
- ⚠️ Правка загрузчика может убить возможность штатного обновления в будущем (дилерский ISTA/WinKFP перестанет проходить проверку).

## 9. Ограничения метода (обязательно к учёту)

1. **PDF-файлы в этой сессии не читаются** — инструмент возвращает `unsupported content type "application/pdf"`. Поэтому ключевые первоисточники по F2MC-16LX (Flash Programming Manual, Hardware Manual MB90390, аппноуты Fujitsu AN07-00142, `PCW16e.pdf`, даташит MB90F395HA) **не были прочитаны полностью**; по ним использованы только заголовки/сниппеты поиска. Это главный пробел отчёта и он закрывается вручную.
2. **Ряд форумов отдаёт HTTP 403 (Cloudflare):** bimmerforums (треда `WinKFP signature error`), cartechnology.co.uk (`.0DA/.0PA TO BIN`, `0pa to bin`), manualzz, community.infineon.com (статья про защиту секторов). Их содержимое не проверено.
3. **`electronix.ru` тред «Реверс инжиниринг МК MB90F395HA»** (ссылка была в результатах поиска: `https://electronix.ru/forum/topic/219645-revers-inzhiniring-mk-mb90f395ha/`) при обращении отдаёт **404** — тема удалена или перемещена. Содержимое неизвестно; **это потенциально важный потерянный источник**, стоит поискать копию.
4. **`KOMB87.prg` отсутствует в рабочей папке** — а именно он определяет режим аутентификации и содержит ключевой материал.
5. Разделы, помеченные 🔶, — **наш собственный анализ файлов**, а не публичные данные; при пересказе вовне их нельзя выдавать за подтверждённые публично.
6. Внутреннее противоречие в `nfsx` (RSA-512 в детальной спеке vs «RSA-1024» в README) — отмечено в §2.1.
