# Пошаговая инструкция: снять дамп защищённой области приборки

Цель этого этапа — получить **16 384 байта** по адресам `0xFFC000–0xFFFFFF`:
загрузчик, векторы CPU, монитор программирования. Это тот артефакт, без
которого нельзя ни понять проверку подписи, ни проектировать обход. Всё
остальное (`SPEICHER_SCHREIBEN`, патч, генератор) начинается после него.

**Риск этапа: нулевой.** Мы только читаем, ничего не пишем.

---

## Почему сначала в машине, а не на стенде

Первый тест отвечает ровно на один вопрос: **отдаёт ли приборка сегмент
`FLASH` через штатный джоб `SPEICHER_LESEN`**. Загрузчик не привязан к VIN и
пробегу, поэтому для ответа годится приборка, **которая уже стоит в машине**.
Донор и стенд на этом шаге не нужны — их подключим, только если понадобится.

---

## Что понадобится

* Windows-ПК с установленными BMW Standard Tools;
* кабель K+DCAN;
* автомобиль с включённым зажиганием;
* 20–30 минут.

---

## Шаг 0. Убедиться, что канал связи уже работает

Это самый важный шаг: если не работает INPA, не заработает и скрипт, и
искать причину надо здесь, а не в Python.

1. Подключить K+DCAN к разъёму OBD-II, включить **зажигание** (двигатель не
   заводить).
2. Запустить **INPA** → выбрать свой кузов → **Kombi** → прочитать что-нибудь
   простое (статус клемм, пробег, версию).

**Критерий готовности:** INPA показывает данные приборки.

Если не показывает:

* драйвер FTDI установлен, и в свойствах COM-порта выставлен
  **Latency Timer = 1 ms** — без этого будут таймауты;
* номер COM-порта в `C:\EDIABAS\BIN\OBD.INI` (секция `[OBD]`, ключ `Port`)
  совпадает с фактическим;
* зажигание включено;
* кабель переведён в режим **D-CAN** (для E9x после ~03/2007).

> **Где что лежит.** `EDIABAS.INI` задаёт интерфейс и каталог ЭБУ — в этой
> сборке секция называется `[Configuration]` (`Interface=STD:OBD`,
> `EcuPath=C:\EDIABAS\ECU`). **COM-порта в `EDIABAS.INI` нет**: при
> `Interface=STD:OBD` порт берётся из `OBD.INI`, секция `[OBD]`. Оба файла
> лежат в `C:\EDIABAS\BIN`. Правьте только `OBD.INI`, и только если порт не
> совпадает: всё остальное уже верно, если INPA/WinKFP/NCS Expert работали с
> этой машиной, — не сломайте конфигурацию.

## Шаг 1. Поставить 32-битный Python

Нужен именно **32-битный**: библиотека `pydiabas` загружает `api32.dll`,
которая 32-битная.

1. Скачать на python.org Windows installer **Windows installer (32-bit)**.
2. Проверить:

```
py -3-32 -V
```

Должно вывести версию. Если команда не найдена — 32-битный Python не встал.

---

## Шаг 2. Поставить pydiabas

```
py -3-32 -m pip install pydiabas
```

## Шаг 3. Разложить скрипт и проверить окружение

Скопировать `kombi_read_flash.py` на Windows, например в `C:\kombi\`.

```
cd C:\kombi
py -3-32 kombi_read_flash.py --check
```

Ожидаемый результат — все пункты без восклицательных знаков. Если написано
`api32.dll не найден в PATH`:

* добавить `C:\EDIABAS\BIN` в переменную `PATH`;
* **закрыть и открыть заново** окно cmd (иначе PATH не перечитается).

> **Тонкость Python 3.8+.** `ctypes.WinDLL("api32.dll")` по имени падает —
> «не найден модуль или одна из его зависимостей» — даже когда каталог есть в
> `PATH`: зависимости библиотеки ищутся не по `PATH`, а по списку каталогов
> загрузки. `pydiabas` этого не задевает, он подставляет полный путь из
> `ctypes.util.find_library`; в своём коде на `ctypes` делайте так же или
> вызывайте `os.add_dll_directory(r"C:\EDIABAS\BIN")`.

### Полная проверка цепочки

`--check` смотрит только Python и `pydiabas`. Всё остальное — установку
EDIABAS, порт, драйвер кабеля и SGBD приборки — проверяет `check_bmw_env.py`.

Если вы работаете из каталога `C:\kombi`:
```
cd C:\kombi
py -3-32 check_bmw_env.py
```

Если запускаете прямо из корня репозитория (`Dash-BMW-e90`):
```
py -3-32 flasher/check_bmw_env.py
```

Он читает `EDIABAS.INI` и `OBD.INI`, сверяет порт из конфигурации с реально
существующими COM-портами, находит в реестре кабель (FTDI/CH340/CP210x) вместе
с `LatencyTimer`, проверяет `KOMB87.prg` в `EcuPath` и сверяет его хеш с
`firmware-manifest.json`. Приборку скрипт **не опрашивает** — машина и кабель
для проверки не нужны.

Код возврата: `0` — всё на месте; `1` — предупреждения (чаще всего «нет ни
одного COM-порта», то есть кабель не подключён); `2` — критично, работать не
получится.

Полезные флаги:

```
--ediabas "D:\EDIABAS"                     другой каталог установки
--firmware-scan "G:\SP-DATEN 67.1"         где искать файлы манифеста
```

`--firmware-scan` ищет проприетарные файлы **по хешу, а не по имени**: в
установке SP-Daten они лежат по своим путям (`E89\data\HKOML2\9316169A.0pa`,
`E53\ecu\KOMB87.prg`) и с другими именами, чем в манифесте. Он же различает
«файла нет» и «файл другой версии» — это важно, потому что `.DAT`/`.HIS`/`.HWH`
разных выпусков SP-Daten совпадают по размеру, но не по содержимому.

## Шаг 4. Проверить связь с приборкой

Ничего не пишет, только читает идентификацию.

```
py -3-32 kombi_read_flash.py --ident
```

Ожидаемый результат: строка `ЭБУ определён: KOMB87` и следом поля
`ID_BMW_NR`, `ID_HW_NR`, `ID_SW_NR_FSV` и прочие.

Скрипт сам перебирает имена ЭБУ (`KOMB87`, `KOMBI` и их варианты с `.PRG`),
поэтому угадывать не нужно.

Если ошибка — **скопировать текст целиком**, он информативный: EDIABAS
возвращает и код, и расшифровку.

## Шаг 5. Снять дамп

```
py -3-32 kombi_read_flash.py --segment LAR --start 0xFFC000 --end 0x1000000 --out boot.bin
```

> **Важно:** на E90 использовать именно `--segment LAR` (по умолчанию). Сегмент
> `FLASH` отклоняется приборкой с `NRC 0x12 (InvalidFormat)`.
> Безопасный размер чанка — 128 байт (установлен по умолчанию, при 254 буфер K-CAN переполняется).

Это 128 вызовов, займёт около 1-2 минут. Прогресс печатается по каждому блоку.
На каждый неудачный вызов скрипт делает до двух повторов.

В конце скрипт сам печатает проверку содержимого:

* долю байт `0xFF` и `0x00`;
* первые 32 байта диапазона;
* хвост диапазона (ближе к `0xFFFFF0`).

**Как понять, что получилось:** хвост **не должен** быть сплошным `0xFF` —
именно там на F2MC-16LX лежит таблица векторов. Если весь диапазон `0xFF` —
значит микроконтроллер аппаратно защищает чтение Flash через OBD в режиме
приложения (что и подтверждено на реальном блоке E90, закрыв H1).

Создаются два файла:

* `boot.bin` — 16 384 байта;
* `boot.manifest.json` — какие адреса реально прочитались и где были ошибки.

`boot.bin` и `boot.manifest.json`. По манифесту сразу видно, полный ли дамп
или с дырами, — это влияет на разбор.

## Если `FLASH` не отдаётся

Сначала убедиться, что сам джоб работает вообще — прочитать другой сегмент:

```
py -3-32 kombi_read_flash.py --segment NVRAM --start 0x000000 --end 0x000100 --out nvram_probe.bin
```

Трактовка:

| Что получилось | Что это значит |
|---|---|
| `NVRAM` читается, `FLASH` нет | сегмент `FLASH` закрыт для чтения приложением → нужен стенд или программатор |
| ничего не читается | проблема в связи, а не в сегменте — вернуться к шагу 0 |
| `FLASH` читается, но всё `0xFF` | попробовать `--segment FLASHX`, затем `LAR` и `ROMX` |

Перебор сегментов — просто повтор команды с другим `--segment`:

```
py -3-32 kombi_read_flash.py --segment FLASHX --start 0xFFC000 --end 0x1000000 --out boot_flashx.bin
```

## Стенд (только если в машине не выйдет)

Приборка на E9x сидит на **K-CAN**, а не на D-CAN. Поэтому на столе:

* питание: `Kl.30` (+12 В), `Kl.31` (масса), `Kl.15` (зажигание — без него
  щиток может не проснуться);
* шина: **K-CAN H/L, 100 кбит/с** — выводы берутся с разъёма приборки, а не с
  OBD (там D-CAN, и он соединён с приборкой через шлюз, а не напрямую);
* терминация **120 Ом** по концам шины — без неё «шина молчит»;
* кабель K+DCAN нужно перевести в режим 100 кбит/с — это уже не «из коробки».

Схема электропроводки есть в Rheingold/ISTA, который у вас на диске.

## Чего НЕ делать на этом этапе

* **Не запускать** `SPEICHER_SCHREIBEN`, `FLASH_LOESCHEN`,
  `FLASH_SCHREIBEN*`, `AUTHENTISIERUNG_START`. Запись — отдельный этап и
  отдельный риск.
* Не прерывать питание во время чтения.
* Не читать `0xFFC000` через `--segment NVRAM` — это другой сегмент, получите
  мусор или ошибку.

## Замечание про C09 (важно для 8 передач)

То, что C09 подходит не всем приборкам, не делает его бесполезным — наоборот.
**C09 содержит готовую реализацию 8 передач** (`D1..D8`, `S1..S8`, `M1..M8`,
знакогенератор плюс CAN-декодер), и она у нас **уже есть** в образах HKOML2
(`9280355A`, `9283869A`, `9316169A`). То есть C09 нужен нам не как то, что
надо залить, а как **референсная реализация**, из которой можно перенести
поддержку 8HP в кастомную сборку под конкретную плату. Это ровно работа для
будущего «генератора» и ещё один аргумент снять дамп загрузчика: без него
непонятно, чем именно проверяется то, что мы будем патчить.
